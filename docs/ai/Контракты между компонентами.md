# Контракты между компонентами

Здесь описаны существующие границы Core и технические соглашения между компонентами. Правила статусов и завершения кампании находятся в [Правилах домена](./Правила%20домена.md), а фактическая готовность частей системы — в [Компонентах](./Компоненты.md).

## Зависимости и текущее подключение

`PackCall.Core` содержит сущности, сценарии и исходящие интерфейсы. `PackCall.Infrastructure` ссылается на Core и содержит модель EF Core. Проекты `PackCall.Api` и `PackCall.Worker` ссылаются на Core и Infrastructure, но пока не регистрируют и не вызывают сценарии Core. Наличие ссылки на проект не означает работающую интеграцию.

В API сейчас зарегистрированы контроллеры и OpenAPI, а бизнес-маршрутов кампаний нет. Worker зарегистрирован как фоновая служба, но пока только периодически пишет сообщение в лог. Метод `AddInfrastructure` настраивает `AppDbContext` с Npgsql, если его вызвать; точки запуска API и Worker его сейчас не вызывают. Эти факты следуют из [API Program.cs](../../src/PackCall.Api/Program.cs), [Worker Program.cs](../../src/PackCall.Worker/Program.cs) и [ServiceCollectionExtensions](../../src/PackCall.Infrastructure/ServiceCollectionExtensions.cs).

## Входящие контракты Core

| Интерфейс | Предоставляет | Зависит от |
| --- | --- | --- |
| [ICampaignService](../../src/PackCall.Core/Services/ICampaignService.cs) | Создание, изменение, удаление, запуск и чтение кампаний; страницы кампаний, доставок и получателей. | `ICampaingRepository`, `IDeliveryRepository`, `IRecipientRepository`. |
| [IDeliveryProcessingService](../../src/PackCall.Core/Services/IDeliveryProcessingService.cs) | Захват пакета, обработку доставки, возврат истёкших закреплений и проверку завершения кампании. | `IDeliveryRepository`, `ICampaingRepository`, `IMessageSender`, `IDeliveryStatusJournal`, `IDeliveryMetrics`. |

Сервисы реализованы в Core и проверяются тестами с подставными зависимостями. Они не являются HTTP API. Возвращаемые сущности и `PageResult<T>` — внутренние типы Core; HTTP-моделей и маршрутов для этих сценариев в приложении пока нет.

Для постраничных методов номер и размер страницы должны быть положительными. Контракты репозиториев требуют сортировки по `Id` и `TotalCount` до пагинации. Запросы доставок и получателей отсутствующей кампании возвращают пустую страницу, если соответствующий репозиторий соблюдает контракт. `GetRecipientsAsync` выбирает уникальных получателей из доставок кампании и ожидает, что репозиторий загрузил `Recipient` вместе с доставкой.

## Исходящие контракты Core

| Интерфейс | Ожидание от реализации |
| --- | --- |
| [ICampaingRepository](../../src/PackCall.Core/Repositorys/ICampaingRepository.cs) | Чтение, страницы и сохранение кампаний. Создание должно сохранять кампанию вместе с её доставками. |
| [IDeliveryRepository](../../src/PackCall.Core/Repositorys/IDeliveryRepository.cs) | Запросы доставок, атомарный захват пакета, возврат истёкших закреплений, сохранение результата и проверка незавершённых доставок. |
| [IRecipientRepository](../../src/PackCall.Core/Repositorys/IRecipientRepository.cs) | Предоставление аудитории для создания кампании. |
| [IMessageSender](../../src/PackCall.Core/Sending/IMessageSender.cs) | Отправка по снимку адреса; `DeliveryId` передаётся как ключ идемпотентности. |
| [IDeliveryStatusJournal](../../src/PackCall.Core/Journaling/IDeliveryStatusJournal.cs) | Приём записей о переходах статуса доставки. |
| [IDeliveryMetrics](../../src/PackCall.Core/Metrics/IDeliveryMetrics.cs) | Учёт захвата, обработки, переходов статуса и результата отправки. |

Фильтры в контрактах репозиториев имеют тип `Expression<Func<TEntity, bool>>`; контракт предполагает их применение к запросу хранилища. Реализаций этих интерфейсов для базы данных пока нет, поэтому перевод выражений в SQL и атомарность операций не подтверждены интеграционным выполнением. Подавление повторной отправки по `DeliveryId` также пока не обеспечено рабочим отправителем. [AppDbContext](../../src/PackCall.Infrastructure/AppDbContext.cs) задаёт EF-модель кампаний, получателей и доставок, но не реализует интерфейсы репозиториев.

## Порядок обработки и сбои

`CaptureBatchAsync` проверяет размер пакета, идентификатор воркера и срок закрепления, затем просит репозиторий захватить не более указанного числа доставок. После ответа репозитория сценарий по очереди записывает переходы в журнал и метрики. `ProcessAsync` передаёт отправителю `SendRequest`, сохраняет конечный статус доставки, обновляет метрики, записывает журнал и проверяет завершение кампании. Эти шаги не заключены в одну транзакцию.

Если отправитель выбросил исключение, `ProcessAsync` не сохраняет конечный статус: доставка остаётся в обработке. Контракт репозитория предусматривает её возврат после истечения закрепления, но рабочей реализации этого механизма пока нет. Если ошибка произошла после сохранения статуса, запись журнала или проверка завершения могла ещё не выполниться. Core не проверяет, что вызвавший `ProcessAsync` воркер владеет закреплением; это обязанность вызывающей стороны. `CancellationToken` передаётся в операции, но отмена не откатывает уже выполненные действия.

Сервисы выбрасывают исключения для неверных аргументов, отсутствующей кампании и запрещённого состояния. Формат HTTP-ошибок и соответствие HTTP-кодам в проекте ещё не определены работающими бизнес-маршрутами.
