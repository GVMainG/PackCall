# Контракты между компонентами

Здесь описаны существующие границы Core и технические соглашения между компонентами. Правила статусов и завершения кампании находятся в [Правилах домена](./Правила%20домена.md), а фактическая готовность частей системы — в [Компонентах](./Компоненты.md).

## Зависимости и текущее подключение

`PackCall.Core` содержит сущности, сценарии и исходящие интерфейсы. `PackCall.Infrastructure` зависит от Core и реализует его интерфейсы через EF Core, PostgreSQL и mock-email. `PackCall.Api` зависит от обоих проектов: регистрирует сценарии управления кампаниями и обработки доставок, HTTP-контроллеры и фоновый `DeliveryWorker`. Отдельного проекта `PackCall.Worker` в текущем дереве нет. Путь вызова от HTTP-запроса до репозиториев и от фонового обработчика до сценария обработки доставок задают [API Program.cs](../../src/PackCall.Api/Program.cs), [ServiceCollectionExtensions](../../src/PackCall.Infrastructure/ServiceCollectionExtensions.cs), [CampaignsController](../../src/PackCall.Api/Controllers/CampaignsController.cs) и [DeliveryWorker](../../src/PackCall.Api/Background/DeliveryWorker.cs).

API берёт строку подключения из `ConnectionStrings:Postgres` и до начала обслуживания запросов вызывает `Database.EnsureCreatedAsync` через `IDbContextFactory<AppDbContext>`. Миграций EF Core в текущем дереве нет, их применение не настроено. [Конфигурация Compose](../../docker-compose.yml) запускает API после проверки готовности PostgreSQL. Автоматического начального наполнения аудитории нет: получателей можно создать через API или отдельный [SQL-скрипт для нагрузочных данных](../../scripts/load-test/seed_100000_recipients.sql). На пустой базе создание кампании не создаст доставок.

## Входящие контракты Core

| Интерфейс | Предоставляет | Зависит от |
| --- | --- | --- |
| [ICampaignService](../../src/PackCall.Core/Services/ICampaignService.cs) | Создание получателей, кампаний и доставок; изменение, удаление, запуск, паузу, возобновление и чтение кампаний; страницы кампаний, доставок и получателей. Создание получателя нормализует email, а повторный адрес завершается [`RecipientAlreadyExistsException`](../../src/PackCall.Core/Exceptions/RecipientAlreadyExistsException.cs). | `ICampaingRepository`, `IDeliveryRepository`, `IRecipientRepository`. |
| [IDeliveryProcessingService](../../src/PackCall.Core/Services/IDeliveryProcessingService.cs) | Захват пакета, обработку доставки с проверкой актуального состояния кампании, освобождение ещё не отправленных доставок при паузе, возврат истёкших закреплений и проверку завершения кампании. | `IDeliveryRepository`, `ICampaingRepository`, `IMessageSender`, `IDeliveryStatusJournal`. |

Сервисы реализованы в Core. Сценарии `ICampaignService` вызываются HTTP-контроллерами; сущности Core преобразуются в отдельные модели ответов API, статусы сериализуются строками. `IDeliveryProcessingService` вызывает фоновый обработчик. В проекте есть тесты с подставными зависимостями и отдельные проверки PostgreSQL и HTTP; условия их запуска указаны ниже.

Пауза и возобновление доступны через `POST /api/campaigns/{id}/pause` и `POST /api/campaigns/{id}/resume`. Оба маршрута возвращают модель кампании с `200`, отсутствие кампании даёт `404`, недопустимый переход или конкурентная смена статуса — `409`. Возобновление может вернуть уже `Completed`, если незавершённых доставок больше нет. Примеры запросов находятся в [PackCall.Api.http](../../src/PackCall.Api/PackCall.Api.http).

Для постраничных методов номер и размер страницы должны быть положительными. Репозитории возвращают элементы в порядке `Id` и общее число до пагинации. HTTP-маршрут доставок отсутствующей кампании возвращает `404`; сам репозиторий доставок для такого `Id` вернёт пустую страницу. `GetRecipientsAsync` для кампании загружает её доставки вместе с `Recipient`, выбирает уникальных получателей и сортирует их по `Id` в памяти перед пагинацией.

## Исходящие контракты Core

| Интерфейс | Существующая реализация и соглашение |
| --- | --- |
| [ICampaingRepository](../../src/PackCall.Core/Repositorys/ICampaingRepository.cs) | [CampaignRepository](../../src/PackCall.Infrastructure/Repositories/CampaignRepository.cs) читает, сохраняет и удаляет кампании. `Get(id)` использует `AsNoTracking`, чтобы получать актуальное состояние внутри обработки батча. `TryUpdateStatusAsync` сохраняет только статус и даты при совпадении ожидаемого статуса в БД. `Create` вызывается до формирования доставок; их порции сохраняются отдельно. |
| [IDeliveryRepository](../../src/PackCall.Core/Repositorys/IDeliveryRepository.cs) | [DeliveryRepository](../../src/PackCall.Infrastructure/Repositories/DeliveryRepository.cs) сохраняет доставки порциями, выполняет выборки и подсчёты. Захват использует SQL с `FOR UPDATE OF delivery SKIP LOCKED` и выбирает только `Waiting` у кампаний `InProgress`. Просроченные закрепления возвращаются отдельным `UPDATE ... RETURNING`. `ReleaseCapturedAsync` освобождает одну доставку только при совпадении `InProgress`, `WorkerId` и `LockExpiresAt`; устаревшее закрепление не освобождает новое. |
| [IRecipientRepository](../../src/PackCall.Core/Repositorys/IRecipientRepository.cs) | [RecipientRepository](../../src/PackCall.Infrastructure/Repositories/RecipientRepository.cs) создаёт получателей и читает их по email, порциями и постранично; уникальный индекс `ix_recipients_email` защищает email от дублей, а нарушение индекса преобразуется в [`RecipientAlreadyExistsException`](../../src/PackCall.Core/Exceptions/RecipientAlreadyExistsException.cs). Наполнение списка не входит в эту реализацию. |
| [IMessageSender](../../src/PackCall.Core/Sending/IMessageSender.cs) | [MockEmailSender](../../src/PackCall.Infrastructure/Sending/MockEmailSender.cs) получает `SendRequest` со снимком адреса и `DeliveryId`, имитирует задержку и возвращает успех или явную ошибку. Успех означает приём провайдером. Реализация не сохраняет результат в PostgreSQL и не использует `DeliveryId` для подавления повторных отправок. |
| [IDeliveryStatusJournal](../../src/PackCall.Core/Journaling/IDeliveryStatusJournal.cs) | [DeliveryStatusJournal](../../src/PackCall.Infrastructure/Journaling/DeliveryStatusJournal.cs) сохраняет записи о переходах в PostgreSQL. |

Фильтры репозиториев имеют тип `Expression<Func<TEntity, bool>>` и применяются к EF-запросу до материализации. Уникальные индексы на email получателя и пару `(CampaignId, RecipientId)` заданы в [AppDbContext](../../src/PackCall.Infrastructure/AppDbContext.cs). Они не обеспечивают идемпотентность внешней отправки; такой механизм в текущем mock-отправителе отсутствует.

## Порядок обработки и сбои

`CampaignService.CreateCampaignAsync` сохраняет кампанию в `Forming`, читает получателей и записывает доставки порциями по 500, затем возвращает кампанию в `Draft`. При ошибке или отмене сценарий пытается удалить частично созданную кампанию. Создание кампании и всех порций доставок не заключено в одну транзакцию; при неудаче очистки частичные данные могут остаться.

`CaptureBatchAsync` проверяет параметры и просит репозиторий атомарно захватить не более указанного числа доставок. После ответа репозитория сценарий по очереди записывает переходы в журнал. `ProcessAsync` передаёт отправителю `SendRequest`, сохраняет конечный статус доставки, записывает журнал и проверяет завершение кампании. Эти шаги не заключены в одну транзакцию.

Запуск, пауза, возобновление и автоматическое завершение используют `TryUpdateStatusAsync` с ожидаемым исходным статусом. Поэтому завершение не перезаписывает уже установленную паузу. Если конкурентный запрос уже установил требуемый статус, `SaveStatusChangeAsync` принимает результат; другой текущий статус приводит к доменной ошибке. При паузе `ProcessAsync` освобождает ещё не отправленную доставку через `ReleaseCapturedAsync` и записывает переход `InProgress` → `Waiting` с прежним `WorkerId`. Освобождение происходит по мере проверки доставок обработчиком; сам HTTP-запрос паузы не освобождает весь пакет. Уже начатая отправка может завершиться после паузы. Проверка кампании перед отправкой и вызов отправителя не составляют одну атомарную операцию.

Если отправитель выбросил исключение, `ProcessAsync` не сохраняет конечный статус: доставка остаётся в обработке до истечения закрепления. [DeliveryWorker](../../src/PackCall.Api/Background/DeliveryWorker.cs) периодически вызывает возврат просроченных доставок и ограничивает время обработки сроком закрепления. Если ошибка произошла после сохранения статуса, запись журнала или проверка завершения могли ещё не выполниться. При возврате просроченного закрепления SQL очищает `worker_id` до создания журнальной записи, поэтому эта запись не содержит прежний идентификатор воркера. В обычной ветке отправки Core не проверяет владельца и срок закрепления; `DeliveryWorker` проверяет их в переданном снимке доставки до вызова Core. Для освобождения при паузе репозиторий дополнительно сравнивает закрепление в БД. `CancellationToken` передаётся в операции, но отмена не откатывает уже выполненные действия.

Обычное исключение в цикле прерывает текущий батч: после `ErrorDelay` обработчик переходит к следующему захвату, а незавершённые доставки прежнего батча остаются до восстановления по сроку. При паузе неотправленные доставки с уже истекающим закреплением также могут быть пропущены воркером до вызова Core и возвращены общим восстановлением. Журналирование возврата при паузе сохраняет прежний `WorkerId`; для возврата по сроку остаётся описанное выше ограничение.

Проверка завершения вызывается после обработки доставки и при возобновлении кампании. Поэтому пустая кампания после обычного запуска остаётся в `InProgress`, а возобновление после паузы завершает её. Явный вызов `CompleteCampaignIfFinishedAsync` также может завершить пустую запущенную кампанию.

[ApiExceptionHandler](../../src/PackCall.Api/Middleware/ApiExceptionHandler.cs) преобразует отсутствие кампании в `404`, неверные аргументы в `400`, доменные ошибки и недоступные операции в `409`; в частности, [`RecipientAlreadyExistsException`](../../src/PackCall.Core/Exceptions/RecipientAlreadyExistsException.cs) при повторном email получает `409` с отдельным значением `ProblemDetails.Title` о существующем получателе. Другие исключения остаются ошибками сервера.

## Настройки фоновой обработки

Секция `DeliveryWorker` в [appsettings.json](../../src/PackCall.Api/appsettings.json) задаёт `Parallelism: 4` и `BatchSize: 10`. [DeliveryWorker](../../src/PackCall.Api/Background/DeliveryWorker.cs) создаёт указанное число асинхронных циклов; каждый захватывает до `BatchSize` доставок и обрабатывает их последовательно. Размер пакета не увеличивает число одновременных отправок: при штатной работе их не больше `Parallelism`. Восстановление просроченных закреплений выполняется отдельным циклом.

По умолчанию [DeliveryWorkerOptions](../../src/PackCall.Api/Background/DeliveryWorkerOptions.cs) задаёт `LockDuration` 90 секунд, `RecoveryInterval` 15 секунд, `IdleDelay` 250 мс и `ErrorDelay` 5 секунд. Срок закрепления отсчитывается с захвата всего батча, включая ожидание очереди внутри пакета. Перед каждой обработкой проверяется оставшееся время с запасом; истекающие доставки пропускаются, а длительная обработка получает отмену до окончания закрепления. Автоматического продления закрепления нет.

При запуске проверяются `Parallelism` от 1 до 64, `BatchSize` не меньше 1, `LockDuration` не меньше 10 секунд, положительные интервалы и сумма `LockDuration + RecoveryInterval` не больше двух минут. Воркер получает `IOptions<DeliveryWorkerOptions>` и сохраняет настройки при создании: для применения изменений нужен перезапуск экземпляра приложения.

## Проверки реализации

[CampaignTests](../../PackCall.Core.Test/CampaignTests.cs), [CampaignWorkflowTests](../../PackCall.Core.Test/CampaignWorkflowTests.cs) и [DeliveryWorkerTests](../../PackCall.Core.Test/DeliveryWorkerTests.cs) проверяют переходы состояний, завершение начатой отправки при паузе и параметры батчей с подставными зависимостями. [CampaignPausePostgresTests](../../PackCall.Core.Test/CampaignPausePostgresTests.cs) проверяет паузу внутри батча, освобождение и повторный захват доставок, конкурентные изменения статуса, защиту нового закрепления и HTTP-маршруты на настоящем PostgreSQL. Эти проверки создают отдельные временные схемы и требуют `PACKCALL_TEST_POSTGRES`; без переменной они пропускаются. Наличие этих сценариев не подтверждает нагрузочные показатели или подавление дублей при неизвестном результате отправки.
