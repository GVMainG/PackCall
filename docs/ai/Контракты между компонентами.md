# Контракты между компонентами

Здесь описаны существующие границы Core и технические соглашения между компонентами. Правила статусов и завершения кампании находятся в [Правилах домена](./Правила%20домена.md), а фактическая готовность частей системы — в [Компонентах](./Компоненты.md).

## Зависимости и текущее подключение

`PackCall.Core` содержит сущности, сценарии и исходящие интерфейсы. `PackCall.Infrastructure` зависит от Core и реализует его интерфейсы через EF Core, PostgreSQL и mock-email. `PackCall.Api` зависит от обоих проектов: регистрирует сценарии управления кампаниями и обработки доставок, HTTP-контроллеры и фоновый `DeliveryWorker`. Отдельного проекта `PackCall.Worker` в текущем дереве нет. Путь вызова от HTTP-запроса до репозиториев и от фонового обработчика до сценария обработки доставок задают [API Program.cs](../../src/PackCall.Api/Program.cs), [ServiceCollectionExtensions](../../src/PackCall.Infrastructure/ServiceCollectionExtensions.cs), [CampaignsController](../../src/PackCall.Api/Controllers/CampaignsController.cs) и [DeliveryWorker](../../src/PackCall.Api/Background/DeliveryWorker.cs).

API берёт строку подключения из `ConnectionStrings:Postgres` и до начала обслуживания запросов применяет существующие миграции EF Core. Конфигурация Compose запускает API после проверки готовности PostgreSQL. Чтение получателей реализовано, но код приложения не заполняет статичную аудиторию: на новой пустой базе создание кампании не создаст доставок.

## Входящие контракты Core

| Интерфейс | Предоставляет | Зависит от |
| --- | --- | --- |
| [ICampaignService](../../src/PackCall.Core/Services/ICampaignService.cs) | Создание получателей, кампаний и доставок; изменение, удаление, запуск и чтение кампаний; страницы кампаний, доставок и получателей. Создание получателя нормализует email, а повторный адрес завершается [`RecipientAlreadyExistsException`](../../src/PackCall.Core/Exceptions/RecipientAlreadyExistsException.cs). | `ICampaingRepository`, `IDeliveryRepository`, `IRecipientRepository`. |
| [IDeliveryProcessingService](../../src/PackCall.Core/Services/IDeliveryProcessingService.cs) | Захват пакета, обработку доставки, возврат истёкших закреплений и проверку завершения кампании. | `IDeliveryRepository`, `ICampaingRepository`, `IMessageSender`, `IDeliveryStatusJournal`, `IDeliveryMetrics`. |

Сервисы реализованы в Core и проверяются тестами с подставными зависимостями. Сценарии `ICampaignService` вызываются HTTP-контроллерами; сущности Core преобразуются в отдельные модели ответов API. `IDeliveryProcessingService` вызывает фоновый обработчик, а не HTTP-маршрут.

Для постраничных методов номер и размер страницы должны быть положительными. Репозитории возвращают элементы в порядке `Id` и общее число до пагинации. HTTP-маршрут доставок отсутствующей кампании возвращает `404`; сам репозиторий доставок для такого `Id` вернёт пустую страницу. `GetRecipientsAsync` для кампании загружает её доставки вместе с `Recipient`, выбирает уникальных получателей и сортирует их по `Id` в памяти перед пагинацией.

## Исходящие контракты Core

| Интерфейс | Существующая реализация и соглашение |
| --- | --- |
| [ICampaingRepository](../../src/PackCall.Core/Repositorys/ICampaingRepository.cs) | [CampaignRepository](../../src/PackCall.Infrastructure/Repositories/CampaignRepository.cs) читает, сохраняет и удаляет кампании. В текущем сценарии `Create` вызывается до формирования доставок; их порции сохраняются отдельно. |
| [IDeliveryRepository](../../src/PackCall.Core/Repositorys/IDeliveryRepository.cs) | [DeliveryRepository](../../src/PackCall.Infrastructure/Repositories/DeliveryRepository.cs) сохраняет доставки порциями, выполняет выборки и подсчёты, атомарно захватывает ожидающие доставки запущенных кампаний и возвращает просроченные закрепления через SQL с `FOR UPDATE SKIP LOCKED`. |
| [IRecipientRepository](../../src/PackCall.Core/Repositorys/IRecipientRepository.cs) | [RecipientRepository](../../src/PackCall.Infrastructure/Repositories/RecipientRepository.cs) создаёт получателей и читает их по email, порциями и постранично; уникальный индекс `ix_recipients_email` защищает email от дублей, а нарушение индекса преобразуется в [`RecipientAlreadyExistsException`](../../src/PackCall.Core/Exceptions/RecipientAlreadyExistsException.cs). Наполнение списка не входит в эту реализацию. |
| [IMessageSender](../../src/PackCall.Core/Sending/IMessageSender.cs) | [MockEmailSender](../../src/PackCall.Infrastructure/Sending/MockEmailSender.cs) использует снимок адреса и `DeliveryId` как ключ идемпотентности. Первый результат сохраняется в PostgreSQL; повторный вызов с тем же ключом возвращает его. |
| [IDeliveryStatusJournal](../../src/PackCall.Core/Journaling/IDeliveryStatusJournal.cs) | [DeliveryStatusJournal](../../src/PackCall.Infrastructure/Journaling/DeliveryStatusJournal.cs) сохраняет записи о переходах в PostgreSQL. |
| [IDeliveryMetrics](../../src/PackCall.Core/Metrics/IDeliveryMetrics.cs) | [DeliveryMetrics](../../src/PackCall.Infrastructure/Metrics/DeliveryMetrics.cs) считает захваты, завершения, смены статусов и результаты отправки; [MetricsController](../../src/PackCall.Api/Controllers/MetricsController.cs) отдаёт `/metrics` с накопительными счётчиками процесса и состоянием доставок из PostgreSQL. |

Фильтры репозиториев имеют тип `Expression<Func<TEntity, bool>>` и применяются к EF-запросу до материализации. Реализации SQL и идемпотентного отправителя существуют в коде; наличие кода и тестов с подставными зависимостями само по себе не подтверждает нагрузочные и аварийные гарантии на PostgreSQL.

## Порядок обработки и сбои

`CampaignService.CreateCampaignAsync` сохраняет кампанию в `Forming`, читает получателей и записывает доставки порциями по 500, затем возвращает кампанию в `Draft`. При ошибке или отмене сценарий пытается удалить частично созданную кампанию. Создание кампании и всех порций доставок не заключено в одну транзакцию; при неудаче очистки частичные данные могут остаться.

`CaptureBatchAsync` проверяет параметры и просит репозиторий атомарно захватить не более указанного числа доставок. После ответа репозитория сценарий по очереди записывает переходы в журнал и метрики. `ProcessAsync` передаёт отправителю `SendRequest`, сохраняет конечный статус доставки, обновляет метрики, записывает журнал и проверяет завершение кампании. Эти шаги не заключены в одну транзакцию.

Если отправитель выбросил исключение, `ProcessAsync` не сохраняет конечный статус: доставка остаётся в обработке до истечения закрепления. [DeliveryWorker](../../src/PackCall.Api/Background/DeliveryWorker.cs) периодически вызывает возврат просроченных доставок и ограничивает время обработки сроком закрепления. Если ошибка произошла после сохранения статуса, запись журнала или проверка завершения могли ещё не выполниться. При возврате просроченного закрепления SQL очищает `worker_id` до создания журнальной записи, поэтому эта запись не содержит прежний идентификатор воркера. Core не проверяет, что вызвавший `ProcessAsync` воркер владеет закреплением; проверку выполняет `DeliveryWorker` до вызова. `CancellationToken` передаётся в операции, но отмена не откатывает уже выполненные действия.

Проверка завершения вызывается после обработки доставки. Поэтому запущенная кампания без доставок остаётся в `InProgress`, хотя явный вызов `CompleteCampaignIfFinishedAsync` мог бы её завершить.

[ApiExceptionHandler](../../src/PackCall.Api/Middleware/ApiExceptionHandler.cs) преобразует отсутствие кампании в `404`, неверные аргументы в `400`, доменные ошибки и недоступные операции в `409`; в частности, [`RecipientAlreadyExistsException`](../../src/PackCall.Core/Exceptions/RecipientAlreadyExistsException.cs) при повторном email получает `409` с отдельным значением `ProblemDetails.Title` о существующем получателе. Другие исключения остаются ошибками сервера.
