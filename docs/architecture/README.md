# Архитектура beta.3

## Компоненты

- **`src/PackCall.Core`** хранит сущности контакта, адреса, кампании, снимка выборки
  и доставки. Сервисы кампаний и обработки доставок используют интерфейсы
  хранилища и оператора `IMessageSender`.
- **`src/PackCall.Infrastructure`** реализует хранение через EF Core и SQL PostgreSQL,
  реестр операторов по каналам и тестовые email-адаптеры `inprocess` и `http`.
- **`src/PackCall.Api`** предоставляет HTTP API контактов, каналов, кампаний и доставок.
  Маршрут `/api/recipients` сохраняет совместимость для email-контактов.
  Ошибки возвращаются как ProblemDetails, OpenAPI доступен в среде Development.
  [Контракт API](../api/README.md).
- **`src/PackCall.Worker`** захватывает доставки пакетами, вызывает оператора канала,
  фиксирует итог и восстанавливает просроченные закрепления.
- **`src/PackCall.Migrator`** применяет EF-миграции и завершает работу. В Compose
  API и Worker стартуют после успешного завершения Migrator. Каждый перед запуском
  проверяет историю миграций через `SchemaGate` в режиме чтения.
- **`src/PackCall.TestEmailOperator`** реализует отдельный HTTP-сервис для режима
  `http`. В режиме `inprocess` Worker использует тестовый адаптер внутри процесса.

## Модель данных

| Таблица | Назначение |
| --- | --- |
| `contacts` | UUID контакта, необязательное отображаемое имя и даты. У перенесённых контактов даты могут быть пустыми. |
| `contact_channels` | Текущие адреса. Один адрес на пару `(contact_id, channel)`. Пара `(channel, address)` уникальна. PATCH контакта заменяет набор адресов целиком в транзакции. |
| `campaigns` | Имя и текст кампании, состояние и даты её жизненного цикла. |
| `campaign_contacts` | Зафиксированные UUID выбранных контактов, ключ `(campaign_id, contact_id)`. |
| `campaign_channels` | Зафиксированные каналы, ключ `(campaign_id, channel)`. |
| `deliveries` | Уникальная пара контакта и канала для кампании, ключ уникальности `(campaign_id, contact_id, channel)`. Внешние ключи связывают её со снимком выборки. `address_snapshot` хранит адрес на момент формирования. Статус, `worker_id`, `lock_expires_at` и даты описывают обработку доставки. У исторической доставки снимок адреса может быть пустым. |
| `delivery_status_journal` | Журнал аудита без внешних ключей. Запись включает время перехода, ID кампании и доставки, идентификатор Worker и результат оператора. Записи добавляются отдельно от обновления статуса и сохраняются при удалении кампании. |

В PostgreSQL статусы кампании представлены числами: `Draft=0`, `InProgress=1`,
`Completed=2`, `Forming=3`, `Paused=4`, `Failed=-1` (действующие операции кампанию
в `Failed` не переводят). Статусы доставки: `Waiting=0`, `InProgress=1`,
`Sent=2`, `Failed=-1`. Эти значения используют и Python-инструменты.
В JSON API статусы представлены строками PascalCase.

Таблица `recipients` и колонки `deliveries.recipient_id` и
`deliveries.recipient_email` относятся к схеме beta.2. Миграция переносит
текущий email в `contact_channels.address`, а исторический адрес доставки в
`deliveries.address_snapshot`, сохраняя UUID контактов и доставок.
Известные email приводятся к нижнему регистру без крайних пробелов. Пустой текущий
email или конфликт текущих адресов после нормализации откатывает миграцию.
Отсутствующий или пробельный исторический адрес становится `NULL`. Незавершённая
доставка с таким снимком недоступна для захвата и может удерживать кампанию в `InProgress`.
[Решение о миграции](../adr/0002-legacy-migration-api-evolution.md).

## Потоки обработки

1. **Снимок выборки.** `POST /api/campaigns` сохраняет кампанию в `Forming`, выбранные
   UUID контактов и каналы одной транзакцией. `all` фиксирует все контакты на момент
   записи выборки, включая контакты без адреса в выбранных каналах. Явная выборка
   учитывает каждый UUID один раз и отклоняется целиком при неизвестном UUID.
2. **Формирование.** Следующая операция соединяет выборку с текущими адресами контактов.
   Для каждой выбранной пары с адресом создаётся одна доставка в `Waiting` с копией
   адреса. Затем API публикует кампанию в `Draft`, в том числе при нуле доставок.
   При сбое или отмене до публикации сервис пытается удалить частично сохранённую
   кампанию со снимком и доставками. Оставшаяся в `Forming` кампания недоступна
   для запуска и захвата. Последующие изменения контакта сохраняют прежние доставки
   и их адреса. [Приёмка SM-2](../evidence/beta3/sm2-audience.md).
3. **Запуск и захват.** `start` проверяет наличие оператора для каждого сохранённого
   канала черновика. Смешанная кампания с Telegram получает `409`, пока оператора
   Telegram нет, даже если email-оператор доступен. Worker берёт только `Waiting`
   из кампаний в `InProgress` с зарегистрированным оператором и непустым снимком
   адреса. PostgreSQL использует `FOR UPDATE SKIP LOCKED` и записывает владельца
   закрепления и срок по часам БД. Пауза блокирует новый захват, а уже начатый
   вызов оператора может завершиться. При обнаружении паузы до вызова Worker возвращает
   захваченную доставку в `Waiting`, если владелец и срок закрепления всё ещё
   совпадают. `resume` продолжает работу с прежними доставками.
4. **Результат и восстановление.** Worker передаёт оператору сохранённый адрес.
   Подтверждённый приём даёт `Sent`, подтверждённый отказ даёт `Failed`, если
   условное обновление подтверждает прежнего владельца и срок действующего
   закрепления. При неизвестном исходе доставка остаётся в `InProgress` до recovery.
   Просроченное закрепление возвращает её в `Waiting` с тем же ID. Если оператор уже
   принял запрос до потери результата, повторный захват может привести к повторному
   вызову. [Приёмка SM-6](../evidence/beta3/sm6-recovery.md).
5. **Завершение.** Worker сверяет кампанию после записи результата и во время recovery
   (при запуске и каждые `RecoveryInterval`). Кампания в `InProgress` переходит в
   `Completed` при отсутствии `Waiting` и `InProgress`, включая исторические
   доставки без адреса в этой проверке. `startedAt` сохраняется, `completedAt`
   устанавливается один раз. `start` и `resume` могут сразу вернуть `Completed`
   при отсутствии незавершённых доставок.

## Границы демо-продукта

Контакт может хранить Telegram chat ID, и кампанию можно сформировать для канала
`telegram`. В beta.3 активен только тестовый оператор email. Поддержка отправки
через Telegram запланирована на beta.4. `Sent` подтверждает приём оператором,
гарантия доставки конечному получателю отсутствует. API предназначен для локального
и демонстрационного стенда, аутентификация, авторизация, multi-tenancy и публичный
SLA находятся за этим пределом. [Матрица гарантий](../guarantees.md).
