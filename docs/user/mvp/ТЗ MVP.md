# ТЗ MVP

Срез реализации: тег `mvp`, коммит `f5dc35787b388466ae687493a5437f5f0c6e44a9` от 22.10.2026. Документ описывает реализованный MVP и отдельно сохраняет планы после него.

## О чём проект и зачем он создаётся

PackCall создаётся для получения опыта разработки высоконагруженных систем с нуля. MVP реализует управление массовой рассылкой через API и фоновую обработку доставок с имитацией email-оператора.

## Основные сущности

Подробные поля, статусы и связи — в [модели данных MVP](Модель%20данных%20MVP.md).

- Кампания — одна массовая рассылка с названием, текстом сообщения и аудиторией.
- Получатель — запись с email в общей аудитории БД.
- Доставка — отправка сообщения одному получателю кампании, снимок его email и текущий результат.
- Журнал смены статусов — технические записи захвата, результата и возврата просроченных закреплений доставок.

## Использование системы пользователем

1. Пользователь подготавливает получателей в БД или добавляет их через API. Внешняя CRM не подключается.
2. Пользователь создаёт кампанию с названием и текстом. Система формирует доставки для всего списка получателей из БД пакетами по 500 и возвращает черновик после окончания формирования.
3. Пока кампания в `Draft`, её можно редактировать. Для запуска название и текст должны быть непустыми.
4. Пользователь отдельно запускает кампанию. Повторный запуск уже запущенной кампании не сбрасывает состояние и не создаёт доставок.
5. Фоновые обработчики передают сообщения mock-email и сохраняют `Sent` или `Failed`.
6. Пользователь читает кампанию со счётчиками ожидающих, обрабатываемых, отправленных и ошибочных доставок; отдельно доступны страницы кампаний, получателей и доставок.

API-маршруты и коды ответов перечислены в [API действиях](API%20действия.md).

## Бизнес-процесс работы системы

Создание и запуск — отдельные операции. Во время формирования кампания имеет статус `Forming`, затем `Draft`, после запуска — `InProgress`. Воркеры захватывают только ожидающие доставки запущенных кампаний.

По умолчанию работают четыре параллельных цикла, каждый захватывает до десяти доставок и обрабатывает свой пакет последовательно. Доставки закрепляются на 90 секунд, просроченные закрепления проверяются каждые 15 секунд.

После конечного результата доставки сервис проверяет завершение кампании. Если не осталось `Waiting` или `InProgress`, кампания становится `Completed`; наличие `Failed` не мешает завершению. Отдельной периодической проверки кампаний без ожидающих доставок нет: пустая кампания и сбой на последнем шаге завершения требуют отдельного внимания.

Подробности и ограничения восстановления — в [сценариях обработки](Сценарии%20обработки.md). Численные цели и сценарии проверки — в [требованиях к нагрузке и гарантиям](Требования%20к%20нагрузке%20и%20гарантиям%20MVP.md); достижение этих целей не следует из наличия кода.

## Границы реализации

- Единственный канал — mock-email, без фактической отправки писем.
- `Sent` означает приём сообщения оператором, а не подтверждение получения адресатом.
- Mock не выполняет дедупликацию по `DeliveryId`; гарантия однократного внешнего эффекта не реализована.
- Аудитория хранится в БД. Для воспроизводимого формирования её нужно подготовить до создания кампании; автоматического пополнения готовой кампании нет.
- Пауза, возобновление и повторная отправка конечной доставки отсутствуют.
- Журнал хранится в PostgreSQL, логи выводятся через Serilog. Сбор метрик и маршрут `/metrics` на теге `mvp` отключены.
- Схема создаётся при старте через `EnsureCreatedAsync`; миграций обновления схемы нет.

## TODO после MVP

### Domain-agnostic архитектура

После MVP отделить движок массовой доставки от конкретной предметной области. Подключаемый доменный модуль должен предоставлять движку список получателей и данные для сообщения, а PackCall — отвечать за общий процесс массовой доставки и хранение её статусов.

В MVP эта архитектура не реализована: система работает с аудиторией из БД и не поддерживает подключение разных доменных модулей.
