# Архитектурные решения MVP

Срез реализации: тег `mvp`, коммит `f5dc35787b388466ae687493a5437f5f0c6e44a9` от 22.10.2026.

## Использование доменных сущностей в EF

`AppDbContext` напрямую использует сущности `Campaign`, `Recipient` и `Delivery` из Core. Отдельные модели хранения для них не добавлены, потому что на этапе MVP структуры доменной модели и хранения совпадают. Дополнительные модели потребовали бы дублирования классов и преобразования данных.

Core не зависит от Entity Framework или PostgreSQL: конфигурация таблиц, связей и индексов находится в Infrastructure. Для журнала используется отдельная инфраструктурная модель `DeliveryStatusJournalRecord`.

Решение следует пересмотреть, если структура базы данных начнёт существенно отличаться от доменной модели или требования хранилища начнут влиять на бизнес-логику.

## PostgreSQL как хранилище очереди

Доставки хранятся в таблице `deliveries`. Отдельного брокера сообщений нет. Захват пакета выполняется одним SQL-запросом: `FOR UPDATE SKIP LOCKED` выбирает доступные записи, `UPDATE ... RETURNING` меняет их статус и возвращает захваченный набор. Выбираются только доставки запущенных кампаний.

Идентификатор воркера и срок закрепления позволяют вернуть зависшую обработку в ожидание. Это не постоянная блокировка и не гарантия однократного внешнего эффекта: сохранение конечного результата не проверяет актуальность закрепления в SQL. Подробнее — в [сценариях обработки](Сценарии%20обработки.md).

## Пакетное формирование кампании

Аудитория читается из БД пакетами по 500 записей; доставки каждого пакета сохраняются через отдельный контекст. Кампания находится в `Forming` до окончания формирования, затем возвращается в `Draft`. Формирование выполняется в запросе создания кампании, без фонового задания и общей транзакции.

При исключении сервис пытается удалить частичную кампанию. После аварийной остановки процесса автоматического восстановления формирования нет. Состав аудитории не защищён общим снимком на весь запрос.

## API и воркер в одном процессе

`DeliveryWorker` работает как hosted service внутри API. По умолчанию четыре цикла параллельно захватывают пакеты до десяти доставок; внутри одного пакета обработка последовательная. Отдельный цикл возвращает просроченные закрепления. Срок действует на весь пакет и не продлевается.

Такой состав развёртывается через Docker Compose вместе с PostgreSQL. Отдельного проекта воркера и конфигурации Docker Swarm на этом срезе нет. План разделения процессов сохранён в [структуре проекта](Структура%20проекта.md).

## Mock-email и смысл успешной отправки

Mock-email только имитирует ответ провайдера. `Sent` означает подтверждение приёма сообщения, а не получение письма адресатом. Реального SMTP или внешнего оператора нет.

В запрос передаётся `DeliveryId`, но mock не хранит результаты вызовов и не использует этот идентификатор для дедупликации. Поэтому документация MVP не заявляет гарантию однократной отправки при сбоях.

## Создание схемы и наблюдаемость

При старте API выполняется `EnsureCreatedAsync`. EF-миграции отсутствуют; существующая схема таким вызовом не обновляется.

Журнал смены статусов хранится в PostgreSQL, логи выводятся через Serilog. Статус доставки и запись журнала фиксируются разными операциями, без общей транзакции. Полнота журнала при сбоях не гарантируется.

Код метрик присутствует, но сбор отключён через `NoOpDeliveryMetrics`, а `MetricsController` исключён из маршрутизации. `/metrics` не является доступной точкой мониторинга на теге `mvp`.
