# Использование доменных сущностей в EF

**Выбрано:** `AppDbContext` сохраняет `Campaign`, `Recipient` и `Delivery` из Core напрямую.

**Альтернатива:** отдельные модели хранения с преобразованием в доменные сущности.

**Почему:** на этапе MVP набор полей и связей совпадает. Отдельный слой добавил бы минимум три класса и время затраты.

# PostgreSQL как хранилище очереди

**Выбрано:** очередь представлена состояниями строк `deliveries` в PostgreSQL. Отдельного брокера нет.

| Вариант | Технические свойства | Оценка для MVP |
| --- | --- | --- |
| Очередь в памяти процесса | Нет сетевого обращения при чтении; содержимое теряется при перезапуске, экземпляры приложения не имеют общей очереди | Потребовались бы восстановление из БД и отдельная координация воркеров |
| PostgreSQL + `SKIP LOCKED` | Задание и его статус находятся в одной строке; захват и смена состояния выполняются одним SQL-запросом | Используется уже необходимое хранилище, без синхронизации с другим сервисом |
| RabbitMQ + PostgreSQL | Брокер выдаёт задания и поддерживает подтверждения; результат и аудит кампании всё равно сохраняются в БД | Добавляет второй сервис, публикацию, подтверждения и восстановление согласованности между БД и брокером |

**Почему PostgreSQL:**

- Созданная строка `Waiting` одновременно является заданием. Нет отдельного шага «сохранить доставку в БД → опубликовать в брокер», между которыми процесс может упасть. При RabbitMQ такой разрыв потребовал бы механизма согласования, например [transactional outbox](https://microservices.io/patterns/data/transactional-outbox.html) с повторной публикацией.
- `FOR UPDATE SKIP LOCKED` пропускает строки, захваченные другой транзакцией; `UPDATE ... RETURNING` в том же запросе переводит выбранные доставки в `InProgress` и возвращает именно этот набор. Отдельные `SELECT` и `UPDATE` без блокировки допускали бы выбор одной доставки несколькими воркерами. Блокировка строк действует на время транзакции захвата; 90-секундное закрепление хранится в полях и не удерживает транзакцию во время вызова оператора. Этот способ применения `SKIP LOCKED` описан в [документации PostgreSQL](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE).
- Для обработки без повторов на одну доставку приходятся два обновления строки: захват и конечный результат; также две записи журнала. При 100 доставках/с это около **200 обновлений строк и 200 вставок журнала в секунду**, плюс чтение кампаний, проверки завершения и служебные запросы. Пакетный захват уменьшает число запросов захвата, но не число изменяемых строк и не устраняет отдельную запись каждого события журнала.
- RabbitMQ не устраняет необходимость идемпотентного обработчика: при сбоях публикация или выдача могут повториться. Поэтому введение брокера само по себе не решает проблему повторного внешнего эффекта. См. [гарантии и повторную выдачу RabbitMQ](https://www.rabbitmq.com/docs/reliability).

**Цена решения и условия пересмотра:** очередь конкурирует с API за ресурсы БД. Частые обновления создают WAL и [устаревшие версии строк, требующие уборки](https://www.postgresql.org/docs/18/routine-vacuuming.html); скорость зависит от индексов, плана захвата, диска и autovacuum. `SKIP LOCKED` не гарантирует строгий FIFO. Брокер следует пересмотреть при необходимости маршрутизации, независимых потребителей, уведомления без опроса либо если замеры покажут.

# Пакетное формирование кампании

**Выбрано:** аудитория читается пакетами по 500 получателей; каждый пакет доставок сохраняется отдельным контекстом. Формирование выполняется внутри HTTP-запроса, без общей транзакции. Кампания находится в `Forming` до окончания создания доставок, затем возвращается в `Draft`.

**Альтернативы:**

- Загрузить всю аудиторию и записать доставки одним контекстом: проще обеспечить одну транзакцию, но все сущности и состояние их отслеживания остаются в памяти до завершения.
- Вынести формирование в фоновое задание: запрос быстрее подтверждается, но нужны отдельные состояние задания, обработка повторов и возобновление после сбоя.

**Почему:** для кампании на 100 000 получателей получается `100 000 / 500 = 200` пакетов. Отдельный контекст ограничивает отслеживаемые доставки размером текущего пакета — 500 вместо 100 000 за весь запрос. Клиент получает `201` только после формирования полного набора; отдельный протокол проверки фонового задания не требуется.

**Ограничения:** запрос может выполняться долго. При исключении сервис пытается удалить частичную кампанию; авария процесса может оставить её в `Forming`. Нет общего снимка аудитории. Если потребуется гарантированное продолжение формирования после перезапуска или создание перестанет укладываться в цель 5 минут.

# API и воркер в одном процессе

**Выбрано:** `DeliveryWorker` запущен как hosted service внутри API. По умолчанию четыре цикла захватывают до десяти доставок каждый; внутри пакета обработка последовательная. Отдельный цикл возвращает просроченные закрепления.

**Альтернатива:** отдельный процесс воркера со своим развёртыванием и масштабированием.

**Почему:** один процесс приложения использует общую регистрацию сервисов, конфигурацию и инфраструктурные реализации; в Compose достаточно приложения и PostgreSQL. Начальная конкурентность ограничена четырьмя вызовами обработки одновременно, а закреплено может быть до 40 доставок на экземпляр. Отдельный процесс не нужен для такой конкурентности сам по себе.

**Ограничения:** API и воркер делят CPU, память и жизненный цикл; рестарт API прерывает обработки, увеличение числа экземпляров API увеличивает и число воркеров. Срок закрепления пакета — 90 секунд, без продления. Разделение оправдано, если нагрузка воркера ухудшает задержки API либо им нужны разные частота обновления и масштабирование. План разделения сохранён в [структуре проекта](Структура%20проекта.md).

# Mock-email и смысл успешной отправки

**Выбрано:** локальная имитация ответа провайдера через `IMessageSender`. Успех сохраняется как `Sent`: оператор подтвердил приём сообщения.

**Альтернативы:** реальный SMTP/API провайдера либо отдельный mock-сервис по сети.

**Почему:** локальный mock позволяет воспроизводить задержку и отказ выбранным адресам без почтовых учётных данных, квот провайдера и влияния его сети. По умолчанию задержка равна 10 мс. Один интерфейс отделяет сценарий обработки от транспорта. Отдельный сетевой mock нужен для проверки сетевых таймаутов и разрывов соединения, но не требуется для проверки доменных переходов.

Подтверждение приёма выбрано конечным успехом MVP, потому что провайдерский ответ не доказывает получение письма адресатом.
