# ТЗ PackCall v1.0.0 — дополнения к MVP

## 1. Реальные каналы отправки

В релизе поддерживаются Telegram, email и SMS с настоящей отправкой сообщений. На каждый канал подключается один оператор. Управление остаётся через API и Swagger; отдельный веб-интерфейс в релиз не входит.

- Пользователь ведёт получателей и их контактные данные внутри PackCall через API.
- У получателя могут быть контакты разных каналов. Кампания содержит выбранные пользователем каналы отправки.
- Пользователь задаёт один общий текст сообщения для всех выбранных каналов.
- Получателю отправляется сообщение по каждому выбранному каналу, для которого у него есть контакт.
- Отсутствие контакта одного канала не блокирует отправку по остальным каналам.
- Пропуск из-за отсутствующего контакта отображается отдельно от ошибки оператора: видны получатель, канал и причина. Доступно количество таких пропусков.
- Контактные данные, используемые конкретной отправкой, фиксируются как снимок соответствующего канала. Общий механизм распространяется на три канала вместо одного email.

Разные каналы обслуживаются отдельными адаптерами отправки при общей обработке кампаний и результатов.

## 2. Ручные группы и сегменты аудитории

Вместо автоматической отправки всей базе получателей пользователь выбирает группы для конкретной кампании.

Поддерживаются два вида групп:

- **Ручная группа:** пользователь явно управляет её участниками.
- **Сегмент по условиям:** состав определяется по признакам получателей.

Кампания может включать несколько групп любого из двух видов. Их участники объединяются без дублей: получатель включается, если входит хотя бы в одну выбранную группу. Попадание в несколько групп не создаёт повторных отправок по одному каналу.

Признаки вроде возраста, пола и места рождения рассматриваются как основа сегментации. Настоящий документ не задаёт невыбранный способ расширения полей и не объявляет доменные плагины необходимой архитектурой.

## 3. Справочник фиксированных статусов

Статусы кампаний и доставок представлены отдельным справочником фиксированных системных состояний, как предусмотрено планом [модели данных после MVP](../mvp/Модель%20данных%20MVP.md).

Пользователь не добавляет произвольные исполняемые состояния и переходы. Правила переходов контролирует приложение. Справочник не превращается в конструктор бизнес-процессов.

## 4. Отдельное приложение Worker

API и Worker разделяются на отдельные запускаемые приложения.

- Worker запускается и перезапускается независимо от API.
- Количество экземпляров Worker изменяется независимо от количества экземпляров API.
- Несколько Worker работают с общей очередью сохранённых заданий.

Основание — план разделения из [структуры проекта](../mvp/Структура%20проекта.md); включение в релиз подтверждено владельцем.

## 5. Автоповторы временных ошибок

Для подтверждённых временных ошибок вводятся ограниченные автоматические повторы с задержкой. Политика повторов содержит настраиваемые предел числа попыток и интервалы ожидания.

- Окончательный отказ не повторяется как временная ошибка.
- После исчерпания разрешённых попыток сохраняется конечная ошибка с причиной.
- Успешная отправка не запускается повторно из-за обычного возобновления кампании.

Потерянный ответ после возможного приёма сообщения оператором не приравнивается к подтверждённому временному отказу. Решение об автоматическом повторе такого вызова пока не включено в согласованную часть требований.

## 6. Нагрузочная цель релиза

Изменение относительно [нагрузочных требований MVP](../mvp/Требования%20к%20нагрузке%20и%20гарантиям%20MVP.md): **одна кампания должна обработать 500 000 доставок не более чем за один час**.

Нагрузочный оператор реализуется как отдельное HTTP API. Worker обращается к нему по сети; локальный вызов mock внутри процесса не заменяет эту проверку.

- Номинальный прогон выполняется без искусственно внесённых сбоев. Час отсчитывается с запуска уже сформированной кампании; подготовка аудитории и формирование измеряются отдельно.
- В час входят сетевые обращения и штатная задержка ответа mock-оператора.
- В нагрузочный объём входят задания отправки; пропуски из-за отсутствия контакта не засчитываются как выполненная отправка.
- Сбои, автоматические повторы и перезапуски проверяются отдельно от номинального часового прогона.
- Результат подтверждается воспроизводимым отчётом: параметры стенда, настройки API/Worker/mock, размер кампании, число запросов и конечных результатов, время начала и завершения.

Приёмка проводится на сервере владельца, в VM с развёртыванием компонентов в Docker.

Ориентир средней скорости для этого объёма — около 139 завершённых доставок в секунду. Требование относится к движку и отдельному mock API; оно не обещает такую же скорость у реальных операторов независимо от их квот.

## 7. Восстановление и защита результатов

В релиз включаются следующие улучшения относительно ограничений, зафиксированных в [сценариях MVP](../mvp/Сценарии%20обработки.md) и [контрактах компонентов](../../ai/Контракты%20между%20компонентами.md):

- Незавершённое из-за сбоя формирование кампании автоматически продолжается после перезапуска без повторного создания уже сформированных заданий.
- Если все доставки получили конечные результаты, но сбой помешал сохранить завершение кампании, система самостоятельно завершает её после восстановления.
- После истечения закрепления поздний результат прежнего Worker не перезаписывает состояние задания, переданного другому Worker.

Эти дополнения закрывают возможность бессрочного зависания служебных переходов и записи устаревшего результата. Они не подменяют отдельный контракт оператора об отсутствии повторного внешнего эффекта.

## 8. Приёмка дополнений

| Дополнение | Проверяемый результат |
| --- | --- |
| Три реальных канала | На контрольные контакты отправлены сообщения через Telegram, email и SMS; на каждый канал используется один подключённый оператор. |
| Несколько выбранных каналов | Получатель с тремя контактами получает общий текст по всем выбранным каналам; результаты доступны отдельно по каналам. |
| Отсутствующий контакт | Отправка по этому каналу пропущена с указанием причины; другие доступные каналы обрабатываются. |
| Ручные группы и сегменты | Можно создать оба вида групп и использовать их в кампании. |
| Пересечение участников групп | Получатель из нескольких выбранных групп включён в аудиторию один раз; повторной отправки по тому же каналу нет. |
| Фиксированные статусы | Приложение использует справочник; произвольное создание новых переходов пользователем недоступно. |
| Отдельный Worker | Worker выполняет обработку при независимом запуске и перезапуске API; возможно несколько экземпляров Worker. |
| Временная ошибка | Подтверждённый временный отказ вызывает повтор с задержкой в пределах настройки; исчерпание попыток даёт конечную ошибку. |
| Формирование после сбоя | После принудительной остановки между пакетами формирование продолжается, повторных заданий нет. |
| Завершение после сбоя | Остановка после последнего результата до сохранения завершения не оставляет кампанию бессрочно запущенной. |
| Устаревший Worker | После истечения закрепления и повторного захвата поздний результат прежнего Worker не изменяет состояние нового закрепления. |
| Номинальная нагрузка | Одна кампания из 500 000 отправок обработана за час через отдельное HTTP API mock-оператора; представлен отчёт. |
