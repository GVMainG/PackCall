# Отложенные вопросы по v1.0.0

Дата: 23.10.2026. Вопросы вынесены из ТЗ и не считаются согласованными требованиями.

## 1. Поля получателей и расширяемость

По просьбе владельца отложен выбор способа добавления признаков получателя: настраиваемые типизированные поля через API, фиксированный набор полей приложения или поля и поведение из доменных модулей.

Примеры признаков из обсуждения: возраст, пол, место рождения. Согласована поддержка ручных групп и сегментов по условиям; схема признаков пока не выбрана.

При обсуждении определить, какие правила нельзя выразить полями и фильтрами, и только затем решить, нужна ли модульная или плагиновая система. Само наличие трёх каналов отправки либо нескольких признаков не обосновывает плагины.

## 2. Группы и сегменты по умолчанию

Владелец предложил предусмотреть группы по умолчанию, а их конкретный состав обдумать позже.

Нужно определить назначение, условия, исходные признаки и обязательность таких групп именно для v1.0.0. Конкретные возрастные интервалы, варианты пола и справочники мест рождения пока не заданы.

## 3. Независимый движок и доменные модули

Необходимость подхода пока не согласована. Согласованный сценарий — пользователь ведёт получателей и задаёт содержание в PackCall; управление осуществляется через API и Swagger.

Решение зависит от вопроса 1: нужны ли предметные правила сверх настраиваемых признаков и сегментов. Адаптеры каналов Telegram, email и SMS имеют отдельное назначение и сами по себе не являются доменными модулями.

## 4. Выбор операторов

По просьбе владельца отложен выбор конкретных операторов Telegram, email и SMS. В релизе требуются реальные отправки, по одному оператору на каждый канал. При выборе определить необходимые контактные идентификаторы, формат сообщения, квоты и способы проверки результата.

## 5. Неопределённый результат отправки

По просьбе владельца решение отложено до выбора операторов. Рассматривается случай: сообщение могло быть принято, но ответ потерялся. Нужно проверить поддержку идемпотентности и получения результата, затем решить, допускается ли автоматический повтор с риском дубля либо требуется отдельный исход для проверки. Не смешивать этот случай с согласованными автоповторами подтверждённых временных ошибок.

## 6. Внешний идентификатор получателя

Владелец решил отложить внешний ID до появления интеграций. Внешний обязательный GUID из TODO модели данных не включён в текущий состав v1.0.0. При появлении сценария обмена определить формат, область уникальности и обязательность ключа.

## 7. Полнота журнала

Владелец отложил выбор гарантии полноты истории. Нужно решить, должны ли сохранённые изменения статусов всегда иметь долговечное событие журнала, какие переходы обязательны и как учитывается сбой между сохранением статуса и записью события. Существующий журнал не является доказательством такой гарантии.

## 8. Доступ к API

Владелец отложил способ доступа к API. Нужно определить границу использования и необходимость API-ключа, учётных записей и разграничения данных. Веб-интерфейс не входит в согласованный объём: используются API и Swagger.

## 9. Ресурсы стенда и профиль mock

Стенд выбран: сервер владельца, VM, развёртывание в Docker. По просьбе владельца точные vCPU, RAM и тип/ограничения диска определяются позже.

До нагрузочной приёмки зафиксировать ресурсы и размещение PostgreSQL, API, Worker и отдельного HTTP mock, задержку ответа и число экземпляров. Номинальный норматив уже согласован: одна готовая кампания, 500 000 доставок за час с момента запуска, без внесённых сбоев; сетевые вызовы и штатная задержка включены.
