## Восстановление

Остановить Api и Worker перед резервным копированием. Выполнить `pg_dump -Fc -f pre-migration.dump` с подключением к исходной БД. Создать отдельные пустые БД для проверки кандидата и восстановления. В каждую загрузить один и тот же дамп через `pg_restore --exit-on-error -d <copy> pre-migration.dump`. В тесте сравнили UUID доставок и получателей, сохранённый email и статусы кампании и доставки в исходной и восстановленной БД.

На копии кандидата запустить новый Migrator с `ConnectionStrings__Postgres` этой копии. Проверить EF history, сравнить ключевые строки с исходными и запустить новые Api и Worker. Для отката направить прежние образы Api и Worker на восстановленную БД с исходной схемой и провести email smoke. Откат восстанавливает состояние на момент дампа. Для применения проверить доступ к дампу и план остановки записей до запуска Migrator.

Полная репетиция на копии с ≥1 млн доставок, измерение блокировок и длительности остаются критериями Story 2.3. Сравнение throughput выполняется в Story 2.6.

На репетиции посчитать незавершённые исторические доставки с пустым снимком адреса. Они сохраняют статус, исключаются из захвата и могут удерживать кампанию незавершённой. При ненулевом результате решение по таким кампаниям нужно принять до выпуска. Старые SQL-фикстуры Python и сиды производительности используют схему beta.2. Их перенос относится к Story 2.5.
