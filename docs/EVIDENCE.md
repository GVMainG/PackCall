# EVIDENCE — правила доказательств PackCall

Статус: принято 2026-11-11 (Epic 1, beta.2). Владелец: мейнтейнер.

Документ фиксирует, как в этом репозитории хранятся доказательства гарантий и результатов.
Любое утверждение о гарантиях (FR-9, FR-10, FR-11, FR-13, NFR-2, NFR-3), воспроизводимости
(FR-20, NFR-5) или готовности релиза (FR-21) должно опираться на воспроизводимую команду и
артефакт, а не на самоотчёт. Это правило обязательно для всех артефактов в `docs/`.

## 1. Канонические пути и имена

Канонические пути (AR-6, addendum §9) перечислены ниже и обязательны; отдельные документы их
не переопределяют:

| Что | Путь |
| --- | --- |
| Архитектура as-is | `docs/architecture/` |
| Матрица гарантий | `docs/guarantees.md` |
| Evidence по тегу | `docs/evidence/<tag>/` |
| Заметки о релизе | `docs/releases/<tag>.md` |
| Архитектурные решения (ADR) | `docs/adr/NNNN-*.md` |
| Контракт API (baseline) | `docs/api/openapi.v1.json` |
| Настоящие правила | `docs/EVIDENCE.md` |

Правила имён:

- `<tag>` — имя тега: веха `beta.N` — тег `v0.5.0-beta.N`, финал — `v0.5.0`; при необходимости
  дополнительного пре-релиза — `v0.5.0-rc.N`, не `beta.6`.
- Имя файла заметок — полное имя тега: `docs/releases/v0.5.0-beta.2.md`.
- Каталог evidence вехи использует короткое имя вехи: `docs/evidence/beta2/` соответствует тегу
  `v0.5.0-beta.2`, `docs/evidence/beta3/` — `v0.5.0-beta.3` и так далее.
- Тематические evidence-каталоги, не привязанные к одному тегу (например,
  `docs/evidence/necessity-audit/`), допустимы; их принадлежность к вехам указывается в README
  каталога.
- Для исторических тегов `mvp`/`v0.5.0-beta.1` заметки не пересоздаются: они доступны через
  `git show` (FR-21).

## 2. Обязательный commit SHA и версия окружения

Каждый evidence-артефакт содержит:

- **полный commit SHA** (40 символов), на котором получен результат: `git rev-parse HEAD`;
- **версию окружения** — то, что влияет на результат: версия .NET SDK, образ/ОС, версия
  PostgreSQL, версия Python и набор зависимостей (для приёмки и замеров);
- **точную команду запуска** с параметрами, чтобы результат можно было воспроизвести;
- дату прогона и, если применимо, идентификатор прогона.

Прогон, на котором снимается evidence, выполняется на чистом рабочем дереве
(`git status --porcelain` пуст); если это невозможно, в артефакте фиксируется незакоммиченный
diff или его хеш, иначе SHA не описывает запущенный код.

SHA берётся напрямую из системы контроля версий и сохраняется как есть, без ручного
переписывания. Артефакт без commit SHA или без команды воспроизведения доказательством не
считается.

## 3. Теги и release notes

- В `docs/releases/<tag>.md` указывается commit SHA, на который выпущен тег.
- SHA в release notes обязан совпадать с SHA тега. **Расхождение — блокер тега**: тег не
  выпускается, пока release notes и evidence не приведены к фактическому SHA.
- Для сверки используется commit SHA, на который указывает тег: `git rev-parse <tag>^{commit}`.
  У аннотированного тега `git rev-parse <tag>` возвращает SHA объекта тега, а не коммита.
- Коммит не может содержать собственный SHA. Поэтому заметки о релизе с SHA тега фиксируются
  отдельным коммитом после постановки тега; release-гейт сверяет SHA из заметок с
  `git rev-parse <tag>^{commit}`. Evidence-артефакты по той же причине коммитятся после прогона:
  их SHA относится к прогону, а не к коммиту самого артефакта.
- Перед постановкой тега release-гейт `scripts/ci/release_gate.py` проверяет по commit SHA, что
  обязательный CI-check `CI required` успешно завершён и опубликован GitHub Actions. Красный или
  отсутствующий check — блокер тега; вывод гейта (check-run id, `html_url`, время) сохраняется в
  `docs/evidence/<tag>/`.
- Тег не переносится и не удаляется; дефект, найденный после тега, исправляется следующим
  релизом. Исключение — компрометация секрета.

## 4. Политика хранения сырых артефактов вне Git

Решение открытого вопроса PRD §8.2.4.

**Хранится в Git** (`docs/evidence/<tag>/`):

- отчёты: README, execution-record, decisions, вывод проверок;
- команды и конфигурации воспроизведения, манифесты;
- сводные JSON/CSV и небольшие скриншоты отчётов;
- всё, что нужно, чтобы проверить утверждение без доступа к машине автора.

**Хранится вне Git** (локально или в артефактах CI):

- сырые многогигабайтные артефакты: журналы выполнения, дампы БД, профили, захваты метрик;
- логи прогонов и контейнеров, если они не являются итоговым evidence-артефактом;
- дампы и выгрузки данных — в Git допускаются только их сводки и команды получения.

Размер сырых артефактов ограничен бюджетом измерений MEAS-3 (addendum §6): файлы сеанса —
не более 2 GiB, collector peak — не более 128 MiB, сверх этого — `inconclusive`. Правила Git не
различают размер файла, поэтому соблюдение политики проверяется на ревью; секретоопасные типы
файлов под `docs/` (`.pfx`, `.pem`, `.key`, `.p12`, `.snk`) остаются игнорируемыми правилами
`.gitignore` и не могут попасть в репозиторий (NFR-4).

Для каждого внешнего артефакта в Git остаётся ссылка: путь или идентификатор, команда
воспроизведения и commit SHA. Срок хранения сырых артефактов не регламентирован: доказательность
сохраняется, пока в Git есть сводка и команда воспроизведения.

## 5. Применение в вехах

- **Epic 1 (beta.2):** переиздание necessity-аудита — `docs/evidence/necessity-audit/`;
  evidence ремонтов приёмки и CI-гейтов — `docs/evidence/beta2/`.
- **Последующие вехи:** `docs/evidence/<tag>/` и `docs/releases/<tag>.md` по тем же правилам.
- Закрытие MEAS-1…MEAS-5 фиксируется в evidence соответствующей вехи: 300k-baseline — на
  коммите тега beta.2 (условие входа Epic 2), 1M-профиль — в beta.5; конкретные артефакты
  определяются Stories 1.13–1.15 и 1.22.
