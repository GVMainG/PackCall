# ADR 0001 — Модель Contact/ContactChannel, снимок выборки и формирование

- **Статус:** принято (beta.2)
- **Дата:** 2026-11-11
- **Связи:** AD-2, AD-3, AD-4, AD-5, AD-8 · FR-1…FR-9, NFR-3, NFR-6 · addendum §2.1, §2.2, §2.3, §2.4, §5

## Контекст

0.5 вводит два канала (`email`, `telegram`) и главную гарантию «отправка только выбранным
контактам и каналам» (FR-9, NFR-3). Текущая модель `recipient` с единственным `email` не
выражает «контакт с несколькими адресами по каналам», а без явного снимка выборки кампании
невозможно отличить «контакт без адреса выбранного канала» от «контакт вне выборки».

## Решение

Целевая модель 0.5 (по addendum §2.1, §2.2):

- **Contact** (`contacts`): `id`, `displayName?`, `createdAt`, `updatedAt`.
- **ContactChannel** (`contact_channels`): `id`, `contactId`, `channel` (`email`|`telegram`),
  `address`; глобальная уникальность `(channel, address)`; DB-ограничение `(contactId, channel)`
  (не более одного адреса на канал у контакта).
- **Campaign** (`campaigns`): без изменений; добавляются счётчики/связи выборки.
- **CampaignContact** (`campaign_contacts`): снимок выбранных контактов (`campaignId`,
  `contactId`).
- **CampaignChannel** (`campaign_channels`): снимок выбранных каналов (`campaignId`, `channel`).
- **Delivery** (`deliveries`): `contactId`, `channel`, `addressSnapshot`; уникальность
  `(campaignId, contactId, channel)`; статусы/закрепление — по AD-4 (перечисления
  `DeliveryStatus`/`CampaignStatus`).

Каноническая форма адреса: `email` — lowercase + trim; `telegram` — целочисленный `chat_id`
(валиден и нормализуется при записи, AD-3). `addressSnapshot` — **копия адреса на момент
формирования** в той же канонической форме; изменение `contact_channels` после формирования не
влияет на доставку.

Инварианты:

1. Доставка существует только для пары «контакт из снимка × канал из снимка», у которой на
   момент формирования был адрес.
2. Уникальность `(campaignId, contactId, channel)` исключает дубли; `(contactId, channel)`
   исключает второй адрес контакта в канале.
3. `addressSnapshot` фиксируется при формировании; изменение `contact_channels` после не влияет
   на доставки; повторное формирование для изменившихся адресов не создаёт доставок (снимок
   неизменяем).
4. Маршрутизация — только по `delivery.channel`; fallback запрещён (AD-3). Отсутствие оператора
   канала — ошибка запуска кампании (FR-16); неизвестный исход — не терминален, recovery после
   истечения закрепления (AD-4).
5. Доставка не создаётся для контакта/канала вне снимка, даже при наличии адреса.
6. Адрес глобально уникален в канале (в канонической форме); два контакта не делят email/chat id.

Снимок выборки — это `campaign_contacts` + `campaign_channels`, а не только сформированные
доставки: так видны контакты без адреса выбранного канала и пропуски. Снимок привязан к моменту
создания кампании (`campaigns.created_at`); отдельной временной метки не требуется — снимок
неизменяем после создания. Доставки образуются пересечением снимка с адресами, существующими на
момент формирования. Формирование синхронное, с видимым статусом `Forming`; сбой формирования —
компенсация по FR-6 (кампания удаляется либо остаётся `Forming` и не запускается; частичные
доставки не отправляются). Предел длительности измеряется, не фиксируется (addendum §5).

## Решение по `CampaignStatus.Failed=-1` (AD-5)

`CampaignStatus.Failed=-1` — недостижимое значение в двуязычном контракте C#/Python. Решение:
значение **остаётся в енуме как явно неиспользуемое**; код, присваивающий или читающий его как
достижимый статус, запрещён (ревью/тест). Удалять немедленно рискованно: Python-приёмка и perf
читают инты статусов напрямую (двуязычный контракт AD-5), и рассинхронизация C#/Python/БД —
источник GAP-01; поэтому удаление — только единой EF-миграцией `beta.3` вместе с обновлением
Python-скриптов.

## Миграция существующих данных

`recipients` → `contacts` + `contact_channels` (`channel=email`, `address=email`);
`deliveries.recipient_id` → `contact_id`, `recipient_email` → `address_snapshot`, добавляется
`channel='email'`; существующие кампании получают `campaign_contacts`/`campaign_channels` по
фактическим доставкам, legacy-режим не вводится. Процедура и контракт эволюции API — ADR 0002
(addendum §2.3).

## Рассмотренные альтернативы (addendum §2.4)

- **Контакт с JSON-массивом каналов** — меньше таблиц, но нет уникальности/индексов и слабее
  гарантия; отклонено.
- **Recipient с фиксированными email/telegram-полями** — просто, но плохо расширяется и
  смешивает адрес и канал; отклонено.
- **Универсальный channel SPI/плагины** — избыточно для двух каналов, противоречит NFR-6;
  отклонено.
- **Выбрано:** нормализованные `contact_channels` + снимок выборки кампании.

## Последствия

- `beta.3` реализует эту модель одной EF-миграцией (addendum §2.3); уникальности — DB-ограничения
  (AD-8), а не только код; необходимые индексы пересечения снимка/адресов (например,
  `campaign_contacts(campaignId)`, `contact_channels(channel,address)`) — деталь beta.3.
- Гарантия FR-9/NFR-3 проверяется на пересечении снимка и адресов; дубли исключены уникальностью.
- Снимки `campaign_contacts`/`campaign_channels` хранятся бессрочно (объём не ограничен);
  пересмотр retention — отдельно, если потребуется.
