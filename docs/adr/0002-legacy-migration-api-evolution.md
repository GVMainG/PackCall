# ADR 0002 — Legacy-кампании при миграции и контракт эволюции API

- **Статус:** принято (beta.2)
- **Дата:** 2026-11-11
- **Связи:** ADR 0001 · AD-5, AD-7 · AR-11 · PRD §8.1 · addendum §2.1, §2.3

## Контекст

`beta.3` переносит модель `recipient` в `contacts`/`contact_channels` и вводит снимок выборки
(ADR 0001). Существующие кампании и доставки не должны потеряться или потребовать ручного
вмешательства; одновременно фиксируется, как API меняется до 0.5 и как такие изменения видны.

## Решение

### Миграция существующих данных (addendum §2.3)

- `recipients` → `contacts` + `contact_channels` (`channel=email`, `address=email`).
- `deliveries.recipient_id` → `contact_id`; `recipient_email` → `address_snapshot`; добавляется
  `channel='email'` для существующих строк. Для строк с `NULL`/пустым `recipient_email`
  `address_snapshot` сохраняет `NULL` (без заглушки).
- Существующие кампании получают `campaign_contacts`/`campaign_channels` по фактическим
  доставкам; **legacy-режим (параллельный legacy-код-путь/dual-write) не вводится** — после
  миграции работает только новая модель.
- Telegram-данных до `beta.3` нет (канал `telegram` добавляется в `beta.4`), поэтому миграция
  переносит только `email`; новых `telegram`-строк создавать не требуется.
- Дедупликация/нормализация — по канонической форме адреса из ADR 0001 (email lowercase+trim);
  миграция идемпотентна (глобальная уникальность `(channel, address)` не допускает дублей при
  повторе).
- Одна EF-миграция (атомарная транзакция). Обязательны: `pg_dump` до миграции, проверенный
  restore, down-миграция **или** задокументированная процедура restore + повторный деплой
  предыдущего тега, проверенная на копии БД. При сбое миграции на середине восстановление — по
  этой же процедуре restore. Репетиция на дампе `beta.1` с ≥1 000 000 доставок (время,
  блокировки, restore) — в evidence `beta.3`; пороговые значения допустимого времени/простоя
  фиксируются там же (не в этом ADR).
- Endpoint `recipients` заменяется `contacts`; до 0.5 breaking changes фиксируются в release
  notes.

### Контракт эволюции API (AD-7)

- Единый envelope списков: `PageResponse{items, pageNumber, pageSize, totalCount, totalPages}`.
- `pageNumber ≥ 1`; `pageSize` default 20, max 100; `totalPages = ceil(totalCount / pageSize)`;
  `pageNumber > totalPages` — пустой `items` (не ошибка); стабильная сортировка по `id`.
- Ошибки — ProblemDetails (поля `type/title/status/detail/instance`; 400 валидация / 404 не
  найдено / 409 конфликт статуса / 500 с компенсацией формирования по FR-6). `401/403` не входят
  в 0.5 — аутентификация/авторизация отсутствуют (NFR-8).
- Wire-спеллинг енумов: статусы — PascalCase (текущий `JsonStringEnumConverter`, замораживается
  OpenAPI baseline в beta.2); `Channel` — lowercase (`email`|`telegram`).
- Версионирование: `v1` — имя baseline-файла (`docs/api/openapi.v1.json`), URL-версии и
  заголовков нет; рубеж `0.5` — продуктовый милстоун (PRD §8.1, тег `v0.5.0`).
- API не объявляется стабильным до 0.5; изменения API диффятся против
  `docs/api/openapi.v1.json`; baseline регенерируется по команде из Story 1.19, расхождение
  кода и baseline — красный флаг ревью и CI-диффа, а не «допустимое расхождение».

## Рассмотренные альтернативы

- **Legacy-режим / dual-write (параллельно старая и новая модель)** — плавнее для клиентов, но
  создаёт две ветви кода и делает миграцию неоднозначной; отклонено — после миграции работает
  только новая модель.
- **Версионировать API в URL (`/api/v1/…`)** — преждевременно для демо-продукта без внешних
  клиентов; версия фиксируется именем baseline-файла.

## Последствия и риски

- Миграция обратима (down-миграция или проверенный restore), решения принимаются до старта
  `beta.3`.
- Смена endpoint `recipients`→`contacts` — осознанный breaking change в release notes `beta.3`.
- Риски: блокировки/время на ≥1M строк (репетиция на дампе `beta.1`), поломка демо-клиентов
  (их нет — NFR-8), потеря данных (закрыта dump/restore). Внешних потребителей нет, поэтому
  deprecation-период не требуется.
