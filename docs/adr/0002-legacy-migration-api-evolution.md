# ADR 0002 — Legacy-кампании при миграции и контракт эволюции API

- **Статус:** принято. Политика обновления beta.3 уточнена 2026-11-19.
- **Дата:** 2026-11-11
- **Связи:** ADR 0001 · AD-5, AD-7 · AR-11 · PRD §8.1 · addendum §2.1, §2.3

## Контекст

`beta.3` вводит `contacts`/`contact_channels` и снимок выборки (ADR 0001).
Изменения API до 0.5 фиксируются в релизных заметках и сверяются с OpenAPI baseline.

## Решение

### Поддерживаемое обновление beta.2 → beta.3

При обновлении разворачивается отдельная пустая PostgreSQL. Migrator применяет
все миграции к новой базе перед запуском API и Worker. Данные beta.2 в новую
базу не переносятся. Старый том остаётся у владельца. Гарантия переноса
распространяется на данные, созданные в 1.0 и позднее, при последующих
поддерживаемых обновлениях. [Инструкция запуска](../../README.md#обновление-с-beta2-до-beta3).

### Историческая репетиция переноса (addendum §2.3)

Этот раздел и подразделы о нормализации, предмиграционной проверке, применении и
откате описывают прежний порядок и результаты Story 2.3 на тестовой копии.

- Каждый `recipient` становится отдельным контактом с прежним UUID и одним каналом `email`.
  Сохраняются идентификаторы кампаний и доставок, ссылки, статусы, даты, аренды и журнал.
  Состав исторических кампаний восстанавливается по фактическим доставкам по [ADR 0001](0001-contact-model-selection-snapshot.md).
- Текущий email переносится в `contact_channels.address`. Исторический `recipient_email`
  переносится отдельно в `deliveries.address_snapshot`. Известные адреса канонизируются.
  Отсутствующий, пустой или целиком пробельный исторический адрес становится `NULL`.
  Текущий email контакта и заглушки никогда не заполняют пустой снимок.
- Миграция `20261113214910_ContactsChannels` атомарно останавливается при пустом текущем email
  или коллизии после нормализации в канале `email`. UUID остаются независимыми, слияния
  контактов нет. После отказа исходная схема и данные остаются в прежнем состоянии.
  Повторный запуск успешно применённой миграции пропускается по журналу EF.
- Доставки `Sent` и `Failed` с пустым снимком сохраняются как история. Worker пропускает
  `Waiting` без адреса при захвате. Истечение аренды может вернуть `InProgress` в `Waiting`,
  где доставка останется недоступной для захвата и может удерживать кампанию незавершённой.
  Отсутствие адреса не является основанием для `Failed`. Этот статус допустим только после
  подтверждённого отказа оператора.
- Основной API модели — `/api/contacts`. В beta.3 маршрут `/api/recipients` сохранён
  для совместимости с email-клиентами. [Текущий контракт](../api/README.md#совместимость-с-beta2).

### Нормализация адресов

Код .NET использует `Trim().ToLowerInvariant()`. Прежний SQL использовал POSIX
`[[:space:]]` с классификацией пробелов базы и `lower(... COLLATE pg_catalog.pg_c_utf8)`.
В среде репетиции PostgreSQL оставлял неразрывный пробел U+00A0 и приводил U+0130 (`İ`) к
`i`. .NET удаляет U+00A0 с краёв и сохраняет U+0130 при инвариантном приведении регистра.

В одной EF-миграции `btrim` получает явное множество пробелов .NET, а `translate` для
Unicode использует однозначные соответствия `Rune.ToLowerInvariant`, вычисленные средой
.NET, запускающей Migrator. Для ASCII применяется преобразование `A–Z` в `a–z`.
Политика применяется к текущим и историческим адресам. Схема и ограничения остаются
прежними. Migrator, Api и Worker выпускаются с согласованной средой .NET и данными
глобализации. Проверки выполняются на UTF-8 базе с настройками целевого релиза.

В Story 2.3 сверяли синтетические ASCII-адреса, пробелы и табуляцию. Повторная проверка после
исправления и проверенные случаи Unicode перечислены в
[evidence репетиции](../evidence/beta3/migration-rehearsal.md). Результаты не устанавливают
эквивалентность всех версий .NET, PostgreSQL и настроек глобализации.

### Историческая предмиграционная проверка beta.2

В репетиции проверку выполняли только на выделенной тестовой копии beta.2
после остановки Api, Worker и остальных источников записи.
Запрос использует то же множество пробелов, что миграция. В beta.2 `Waiting = 0`,
`InProgress = 1` для доставок. Счётчик кампаний включает `Draft = 0`, `InProgress = 1`,
`Forming = 3` и `Paused = 4`.

```sql
SELECT count(*) AS pending_deliveries_without_address,
       count(DISTINCT campaigns.id) FILTER (WHERE campaigns.status IN (0, 1, 3, 4))
           AS affected_unfinished_campaigns
FROM deliveries
JOIN campaigns ON campaigns.id = deliveries.campaign_id
WHERE deliveries.delivery_status IN (0, 1)
  AND (
      deliveries.recipient_email IS NULL
      OR btrim(deliveries.recipient_email,
          U&'\0009\000A\000B\000C\000D\0020\0085\00A0\1680\2000\2001\2002\2003\2004\2005\2006\2007\2008\2009\200A\2028\2029\202F\205F\3000') = ''
  );
```

Если первый счётчик ненулевой, приостановите выпуск для этой базы. Для разбора замените
оба агрегата на `deliveries.id, campaigns.id, deliveries.delivery_status, campaigns.status`
с теми же JOIN и WHERE. Владелец данных определяет судьбу затронутых кампаний,
включая несогласованные статусы доставки и кампании. Запись и отправки остаются
закрыты до его решения. Если решение меняет исходную БД, повторите проверку и снимите
новый дамп после согласованных изменений. При нуле можно продолжить при прохождении
остальных сверок. Терминальные доставки с отсутствующим адресом сохраняются при любом
результате проверки.

### Историческое применение и откат на тестовой копии

Команды ниже воспроизводят репетицию Story 2.3. Все подключения, включая
исходное, указывают на выделенные тестовые БД. Поддерживаемое обновление
использует отдельную пустую базу по инструкции выше.

1. Остановите Api и Worker beta.2, дождитесь завершения операций и остановите остальные
   источники записи. Проверьте, что подключение указывает на нужную БД с историей EF beta.2.
   Для повторной проверки на пробной БД, где уже применили прежний ContactsChannels,
   восстановите копию beta.2. Выполните предмиграционную проверку и сохраните исходное состояние.
2. Создайте резервную копию через
   `pg_dump -Fc -d <beta2_source_connection> -f pre-migration.dump`. Проверьте её
   восстановлением в отдельную пустую БД командой
   `pg_restore --exit-on-error -d <empty_db> pre-migration.dump`. Сверьте исходную схему,
   историю EF и контрольные данные. Храните проверенный архив до окончания окна отката.
3. Подключите Migrator beta.3 к тестовой копии и дождитесь успешного
   завершения `20261113214910_ContactsChannels`. До запуска Api и Worker сверьте историю EF,
   UUID, связи, статусы, журнал, исторические адреса и состав снимков с исходными данными.
   Миграция должна сохранить пустые снимки кампаний без доставок.
4. После успешных сверок запустите Api и Worker beta.3, проверьте готовность схемы и
   выполните контрольный запрос и тестовую отправку в контролируемом сценарии.
5. При необходимости отката остановите Api, Worker и прочие записи. Восстановите архив
   в отдельную пустую БД через `pg_restore --exit-on-error`, проверьте историю EF и
   исходные данные. Восстановленная БД содержит состояние на момент дампа. До открытия
   записи и запуска Worker сверьте операции после дампа по сохранённому состоянию новой БД
   и журналам, включая подтверждённые и неопределённые исходы отправок. При риске повторной
   отправки держите Worker остановленным до решения по затронутым доставкам. После сверки
   направьте Api и Worker `v0.5.0-beta.2` на восстановленную БД и проверьте готовность схемы.

В [Story 2.3](../evidence/beta3/migration-rehearsal.md) на 1 000 000 синтетических доставок
применение и откат заняли суммарно 82,047 с при лимите 1 800 с. Пробные чтения `deliveries`
и `recipients` ожидали эксклюзивных блокировок Migrator по 30,937 с. На этой выборке
предмиграционная проверка даёт 10 000 незавершённых доставок в 75 приостановленных
кампаниях. Это показатели прогона Story 2.3 на копии схемы beta.1 с откатом на beta.2.
Рабочая нагрузка и длительные транзакции в замере отсутствовали.
После исправления нормализации повторный прогон занял суммарно 83,219 с. Пробные чтения
с ожиданием блокировки заняли по 34,687 с. Оба прогона описаны в том же evidence.

### Контракт эволюции API (AD-7)

- Единый envelope списков: `PageResponse{items, pageNumber, pageSize, totalCount, totalPages}`.
- `pageNumber ≥ 1`; `pageSize` default 20, max 100; `totalPages = ceil(totalCount / pageSize)`;
  `pageNumber > totalPages` — пустой `items` (не ошибка); стабильная сортировка по `id`.
- Ошибки — ProblemDetails (поля `type/title/status/detail/instance`; 400 валидация / 404 не
  найдено / 409 конфликт статуса / 500 с компенсацией формирования по FR-6). `401/403` не входят
  в 0.5 — аутентификация/авторизация отсутствуют (NFR-8).
- Wire-спеллинг енумов: статусы — PascalCase (текущий `JsonStringEnumConverter`, замораживается
  OpenAPI baseline в beta.2); `Channel` — lowercase (`email`|`telegram`).
- Версионирование: `v1` — имя baseline-файла (`docs/api/openapi.v1.json`), URL-версии и
  заголовков нет; рубеж `0.5` — продуктовый милстоун (PRD §8.1, тег `v0.5.0`).
- API не объявляется стабильным до 0.5; изменения API диффятся против
  `docs/api/openapi.v1.json`; baseline регенерируется по команде из Story 1.19, расхождение
  кода и baseline — красный флаг ревью и CI-диффа, а не «допустимое расхождение».

## Рассмотренные альтернативы

- **Legacy-режим / dual-write (параллельно старая и новая модель)** — плавнее для клиентов, но
  создаёт две ветви кода и делает миграцию неоднозначной; отклонено — после миграции работает
  только новая модель.
- **Версионировать API в URL (`/api/v1/…`)** — преждевременно для демо-продукта без внешних
  клиентов; версия фиксируется именем baseline-файла.

## Последствия и риски

- Для возврата к beta.2 используется её исходная установка с сохранённым томом.
  Сценарий восстановления из дампа относится к исторической репетиции.
- Обязательная выборка и каналы в `POST /api/campaigns` меняют требования к клиентам
  beta.2. Изменения контракта фиксируются в release notes.
- Продолжительность блокировок и число проблемных доставок из исторической репетиции
  зависят от содержимого БД и окружения. Внешних потребителей API нет (NFR-8),
  поэтому deprecation-период не требуется.

контактов, формировании снимков и маршрутизации операторов. Текущими
потребителями абстракций остаются API и Worker, реестр использует keyed DI.
