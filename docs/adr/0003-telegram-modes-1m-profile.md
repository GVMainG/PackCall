# ADR 0003 — Режимы Telegram и профиль multi-worker/1M

- **Статус:** принято (beta.2)
- **Дата:** 2026-11-11
- **Связи:** AD-1, AD-3, AD-4 · FR-17, FR-18, NFR-1 · AR-10, AR-12 · SM-1, SM-C4 · addendum §4, §5, §6

## Контекст

`beta.4` добавляет Telegram-оператор (внешняя зависимость, секрет, лимиты Bot API), а `beta.5`
сертифицирует 1M/ч. Оба контракта фиксируются до реализации, чтобы не менять их задним числом и
не ослаблять гарантии. Здесь «0.5» — финальный релиз (тег `v0.5.0`), `beta.N` — предрелизы.

## Решение

### Матрица режимов Telegram (AR-12, addendum §4)

Переменные: `TELEGRAM_SEND_MODE=disabled|fake|live` и `TELEGRAM_API_BASE_URL` (default — реальный
Bot API). Валидные комбинации — только три строки таблицы:

| Режим | `TELEGRAM_API_BASE_URL` | Токен | Поведение |
| --- | --- | --- | --- |
| `disabled` | любой | не требуется | отправка запрещена |
| `fake` | не-default (поддельный Bot API) | фиктивный (не проходит реальный Bot API) | отправка в поддельный сервер |
| `live` | default (реальный Bot API) | реальный (валидируется `getMe`) | отправка в реальный Bot API |

Любая иная комбинация (в т.ч. `fake` + default URL, `live` + не-default URL, `live` + фиктивный
токен) — **ошибка старта**. `TELEGRAM_SEND_MODE` не задан — по умолчанию `disabled` (безопасно).
Механизм проверки «реальности» токена и формат поддельного сервера — деталь `beta.4`.

Токен — только из env/секрета (`TELEGRAM_BOT_TOKEN`), не в Git/логах/артефактах/ответах. Retry/
backoff в 0.5 **нет**; recovery = повтор попытки после истечения закрепления (медленно, без
гарантии порядка) — это не retry-политика. Бот пишет только пользователю, начавшему диалог
(`/start`); текст ≤4096 символов — кампания с Telegram и текстом длиннее отклоняется на создании
(`400`). **Allowlist чатов для `live` и поведение при `/start` от произвольных пользователей —
открытый вопрос (addendum §12), решение в ADR `beta.4`.**

### Профиль multi-worker/1M (AR-10, addendum §5)

«Профиль» — зафиксированный набор параметров прогона: заранее сформированная кампания на
1 000 000 доставок (email, mock HTTP, `simulate_errors=false`), ≥2 Worker на общей очереди
PostgreSQL; окно «запуск → последний `Sent`» ≤60 минут; формирование и подготовка вне окна.
«Запуск» = старт кампании через API; `Sent` фиксируется по подтверждению оператора; время — по
часам БД (`clock_timestamp()`, AD-4), а не процессам Worker (исключает clock skew).

Multi-worker не требует новой архитектуры: состояние и координация — только PostgreSQL
(AD-1); конкурентный захват — `FOR UPDATE SKIP LOCKED`, условная фиксация, закрепление и
recovery — по AD-4.

Бюджет инструментации — MEAS-3 (addendum §6), проверяется парными прогонами off/on: медиана
потери throughput ≤5%, p95 processing ≤10%, Worker diagnostics ≤16 MiB, collector peak ≤128 MiB
и ≤0.1 CPU, файлы ≤2 GiB/сеанс.

Порядок `beta.5`: тюнинг (индексы/батчи/recovery) → функциональная регрессия → финальный
1M-замер → заморозка; после сертификации изменение worker-пути/схемы/индексов/батчей/
инструментации требует повторного замера. Число Worker фиксируется в отчёте `beta.5`, верхняя
граница не задаётся; критерии остановки прогона — runbook `beta.5` (деталь, не в этом ADR).

300k-сеанс даёт только экстраполяцию (≈1,25M/ч на одном Worker), **не сертификацию**: контеншн
на 1M строк, два Worker и качество инструментации неизвестны.

Генератор 1M-датасета — деливерабл `beta.5` (детерминированный SQL/скрипт в `scripts/`, команда
в Git, датасет вне Git); `seed_100000_recipients.sql` на 100k недостаточен.

## Следствия и ограничения

- Координация и состояние доставок — только PostgreSQL (AD-1); брокер/кэш/очередь не вводятся.
- Операторы резолвятся keyed-реестром `Channel → IMessageSender` (AD-3); ровно один активный
  оператор на канал; Telegram — функциональный канал, throughput 1M не заявляется (SM-C4).
- SM-1 — блокирующая метрика 0.5: при FAIL `beta.5` не тегируется; владелец выбирает новый стенд
  или явно меняет NFR-1 правкой PRD до тега.

## Рассмотренные альтернативы

- **1M через Telegram** — физически ограничено лимитами Bot API; отклонено.
- **Оптимизация Telegram под throughput** — не цель (SM-C4); отклонено.
- **Брокер/очередь для multi-worker** — нарушает AD-1; отклонено.

## Трассировка

AD-1 (координация только через БД), AD-3 (seam/реестр операторов), AD-4 (машина состояний и
захват), FR-17 (секреты), FR-18 (multi-worker), NFR-1 (1M), AR-10 (1M-профиль), AR-12
(Telegram-матрица), SM-1, SM-C4, addendum §4, §5, §6. Документ — вход для стори `beta.4`/`beta.5`.
