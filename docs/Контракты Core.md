# Контракты Core

## Направление зависимостей

`PackCall.Api` вызывает сценарии через интерфейсы `ICampaignService` и
`IDeliveryProcessingService` из `PackCall.Core.Services`. Контроллеры и фоновые
обработчики не обращаются к `DbContext` и не меняют статусы сущностей напрямую.

`PackCall.Infrastructure` реализует исходящие интерфейсы Core: репозитории,
отправитель сообщений, журнал и метрики. Для хранения не нужно вызывать
сценарии Core из репозиториев. Core не зависит от ASP.NET Core, EF или PostgreSQL.

## Сценарии кампании

| Метод `ICampaignService` | Результат и повторные вызовы |
| --- | --- |
| `CreateCampaignAsync` | Id нового черновика с одной доставкой на каждый уникальный Id получателя. Адрес сохраняется как снимок. Каждый вызов создаёт новую кампанию |
| `StartCampaignAsync` | Запускает черновик. Для уже запущенной кампании ничего не изменяет. Завершённую кампанию нельзя запустить повторно |
| `UpdateCampaignAsync` | Возвращает изменённый черновик. Название и текст передаются целиком, преобразование частичного HTTP-запроса выполняет API |
| `DeleteCampaignAsync` | Возвращает `true` при удалении, `false` при отсутствии кампании. Удаление запущенной кампании запрещено |
| `GetCampaignAsync` | Сущность кампании или `null` |
| `GetCampaignsAsync` | `PageResult<Campaign>` |
| `GetDeliveriesAsync` | `PageResult<Delivery>` для указанной кампании |
| `GetRecipientsAsync` | `PageResult<Recipient>` с уникальными получателями указанной кампании |

Нумерация страниц начинается с 1, размер страницы должен быть положительным.
Элементы упорядочены по Id. `TotalCount` — число всех подходящих элементов до
пагинации. Для отсутствующей кампании страницы доставок и получателей пустые.
Название и текст черновика могут быть незаполнены; при запуске оба обязательны.

Сущности и `PageResult<T>` — внутренние результаты приложения. API преобразует
их в собственные HTTP-модели и не сериализует граф навигационных свойств напрямую.
Статистика доставок и HTTP-модели этим контрактом пока не предоставляются.

## Сценарии обработки

| Метод `IDeliveryProcessingService` | Результат и условия |
| --- | --- |
| `CaptureBatchAsync` | Не более указанного размера пакета. Захватываются только ожидающие доставки запущенных кампаний. Размер пакета и срок закрепления положительны, Id воркера заполнен |
| `ProcessAsync` | Доставка из захваченного пакета передаётся отправителю. Успех переводит её в `Sent`, явная ошибка — в `Failed`. Результат сохраняется, записываются журнал и метрики, проверяется завершение кампании |
| `ReleaseExpiredLocksAsync` | Число доставок, возвращённых в `Waiting` после истечения закрепления |
| `CompleteCampaignIfFinishedAsync` | `true`, если этот вызов завершил кампанию; иначе `false`. Ошибочные доставки не препятствуют завершению. Повторная проверка не изменяет даты. Кампания без доставок также может быть завершена |

Обработчик передаёт в `ProcessAsync` только доставку, захваченную им, до истечения
закрепления. Core не проверяет владение закреплением сравнением с текущим воркером.
Повторная обработка доставки в конечном статусе запрещена. Отправитель получает
`DeliveryId` как ключ идемпотентности; подавление повторной отправки обеспечивает
реализация `IMessageSender`.

## Ошибки и отмена

Все операции принимают `CancellationToken`. Отмена сообщается через
`OperationCanceledException` и не означает откат уже сохранённых изменений.
Технические исключения внешних зависимостей передаются вызывающему коду.

- `KeyNotFoundException`: кампания не найдена при запуске, изменении,
  обработке её доставки или проверке завершения.
- `InvalidStatusTransitionException`: запрещённый переход статуса кампании.
- `DomainException`: доставка не в обработке либо её кампания не запущена.
- `InvalidOperationException`: редактирование не черновика или удаление запущенной кампании.
- `ArgumentException` и его подклассы: неверные аргументы; в том числе
  незаполненные данные, недопустимая пагинация, null вместо доставки.

API назначает HTTP-коды и формат ошибок. Core не содержит HTTP-ответов.
При исключении отправителя результат доставки не фиксируется; её закрепление
сохраняется до восстановления по сроку. Сохранение статуса, журнал, метрики и
проверка завершения выполняются последовательно и не образуют общей транзакции:
исключение после сохранения статуса не означает, что доставка ещё не обработана.

## Обязанности Infrastructure

- `ICampaingRepository`: атомарно сохраняет новую кампанию и её доставки,
  не создавая существующих получателей повторно.
- `IDeliveryRepository`: атомарно захватывает доставки запущенных кампаний,
  возвращает истёкшие закрепления, сохраняет результаты и проверяет наличие
  незавершённых доставок. Запрос доставок с фильтром загружает `Recipient`.
- `IRecipientRepository`: предоставляет заранее заданную аудиторию MVP.
- `IMessageSender`: использует `SendRequest` и `SendResult`, обеспечивает
  идемпотентность по `DeliveryId` для mock-email.
- `IDeliveryStatusJournal` и `IDeliveryMetrics`: сохраняют записи и публикуют метрики.

Фильтры репозиториев имеют тип `Expression<Func<TEntity, bool>>`.
Реализация применяет их к запросу до загрузки данных. Выражения должны допускать
перевод в SQL; произвольные вызовы методов внутри выражения не гарантируются.

## Подключение

Точка сборки приложения регистрирует сценарии как scoped-зависимости:

```csharp
services.AddScoped<ICampaignService, CampaignService>();
services.AddScoped<IDeliveryProcessingService, DeliveryProcessingService>();
```

Также должны быть зарегистрированы все исходящие интерфейсы с реализациями из
Infrastructure. Каждый пакет фоновой обработки выполняется в отдельном scope,
чтобы не использовать один DbContext из нескольких потоков. HTTP-контроллер
получает `ICampaignService`, фоновый обработчик — `IDeliveryProcessingService`.

Это схема подключения; реализации репозиториев PostgreSQL, отправителя и
наблюдаемости, а также рабочие HTTP-endpoints относятся к следующим задачам.
