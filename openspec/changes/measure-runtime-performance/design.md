Прочитанные базовые спецификации `delivery-processing`, `delivery-status-journal`, `worker-coordination`, `delivery-observation`, `test-email-operator` согласуются с этими границами. Их бизнес-контракты не меняются. Папка `docs/` отсутствует; ссылки старых README на `_bmad-output` не считаются существующей системой хранения результатов.

## Goals / Non-Goals

**Goals:** сравнимые во времени агрегаты с ограниченной памятью, независимая от финального отчёта запись, воспроизводимые файлы для офлайн-анализа, явная неполнота и возможность опровергнуть гипотезу о замедлении.

**Non-Goals:** exactly-once внешняя отправка, аудит всех попыток, распределённые трассы через Python, исправление пропусков бизнес-журнала, увеличение lease, изменение SQL/индексов/параллелизма ради скорости. Наблюдаемость не должна исправлять существующие дефекты завершения кампании.

## Decisions

### 1. Подтверждённый профиль и зафиксированные допущения

Подтверждено пользователем: Windows локально, Docker Desktop + Compose, HTTP-оператор, ошибки выключены, одна кампания на 300 000 доставок, завершение по прогону. Никакой заданной длительности и пополнения. Сеанс охватывает запуск кампании и всю обработку; формирование данных — подготовительная фаза.

Допущения первого профиля: один Worker, P=4, B=10, LockDuration=90 s, RecoveryInterval=15 s, IdleDelay=250 ms, ErrorDelay=5 s, timeout HTTP=5 s, `PACKCALL_ENVIRONMENT=test`. Это явные значения профиля, а не догадка о фактически запущенных контейнерах. Один API, одна PostgreSQL, один HTTP-оператор; Release images, без debugger/hot reload/VS fast mode. Синтетические одинаковой длины сообщения и email в отдельной БД; нет сторонних кампаний. Ресурсные лимиты не придумывать: preflight фиксирует Windows CPU/RAM, WSL2/Hyper-V backend, доступные Docker VM CPU/RAM/swap, ограничения каждого контейнера и тип/место volumes. Если лимита нет, записать `unlimited`, а не ноль.

Верхний аварийный timeout опционален и не определяет длительность успешного прогона. Ctrl+C/timeout/потеря прогресса дают `aborted`/`stalled`, а не успешный результат. При всех терминальных доставках и незавершённой кампании после согласованного в профиле контрольного ожидания 120 s driver фиксирует `completion_stalled`, сохраняет данные и штатно останавливает процессы без исправления статуса.

### 2. Счётчики и границы операций

Метрики .NET `Meter`/`Counter<long>`/`Histogram<double>` с малым фиксированным набором меток: операция, исход, назначение журнала, категория ошибки. `Stopwatch`/TimeProvider для интервалов; UTC только для корреляции. Инструментирование не меняет публичный возврат ProcessAsync или доменные сущности: исходы фиксируются непосредственно в существующих ветках, репозитории/адаптеры можно обернуть. Контекст попытки внутри процесса временный и освобождается после обработки. Все операции заканчиваются регистрацией длительности в finally, кроме убитых процессов; исключения пробрасываются прежним образом.

| Серия | Начало → конец, включённые затраты |
|---|---|
| `capture.storage` | Вход в CaptureBatchAsync репозитория → возврат материализованного пакета/ошибка |
| `capture.total` | Вход в сервис захвата → возврат после записей журнала пакета/ошибка |
| `batch.wait` | Локальный момент возврата пакета из репозитория → начало ProcessCapturedAsync конкретной строки; включает capture-journal и предшествующие строки |
| `lease.check` | Получение времени БД и расчёт остатка → готовность к вызову ProcessAsync/пропуск |
| `processing.total` | Вход ProcessCapturedAsync → окончание всех его действий; отдельно started service и исход ветки |
| `operator.call` | Вход IMessageSender.SendAsync → разобранный SendResult/исключение; сериализация, сеть, сервер, чтение, проверка ответа |
| `result.persist` | Вход TryCompleteAsync → true/false/исключение; включает ожидание соединения и блокировок |
| `journal.append` | Вход AppendAsync → конец SaveChanges/dispose; назначение capture/terminal/recovery/pause |
| `campaign.check` | Вход CompleteCampaignIfFinishedAsync → return/ошибка; чтение кампании и pending-check |
| `campaign.persist` | Условный TryUpdateStatusAsync для Completed → подтверждение/неприменение/ошибка |
| `recovery.storage` | Вход репозитория ReleaseExpiredLocksAsync → материализованные освобождённые строки/ошибка |
| `recovery.total` | Вход recovery сервиса → конец всех записей журнала/ошибка; периодический Delay не входит |

В `processing.total` входят загрузка кампании и lease-check; `batch.wait` в него не входит. Не складывать родительские и дочерние длительности как независимые затраты. Recovery и обработка выполняются параллельно. Суммы длительностей нескольких lanes могут превышать стеночное время.

Счётчики (целые события/строки, не скорости):

- `terminal.applied{status=sent|failed}` увеличивается сразу после подтверждённого `true` из хранилища, прежде следующей проверки отмены; total — сумма двух статусов. Это наблюдённые подтверждения, не все возможные commit при потере ответа.
- `processing.finished{outcome=terminal_path_complete|stale_result|paused_release|paused_no_release|lease_skipped|invalid_capture|error|cancelled}`; `terminal_path_complete` требует сохранения + журнала + возврата проверки кампании. Подтверждённый Failed тоже может завершить путь без технической ошибки. Дополнительно фиксируется `after_terminal_applied` для сбоя/отмены после сохранения.
- `operator.finished{accepted|rejected|validation|service|protocol|transport|timeout|cancelled|other}`; `result.finished{applied|not_applied|error|cancelled}`; причина отмены host/lease/other.
- `capture.calls`, `capture.empty`, `capture.rows`, `processing.started`, `service.started`, `journal.finished` по исходу и назначению, `campaign.checks`, `campaign.completed`, `recovery.calls`, `recovery.rows` (при возврате из SQL, даже если журнал затем упал).

Не делать DeliveryId/RecipientId/AttemptId/CampaignId метками метрик. SessionId и ProcessInstanceId — envelope экспортируемого файла; WorkerId — отдельное отображение в manifest. Число категорий ошибок фиксировано, без message/stack/payload.

**Повторы:** attempt означает новый вход ProcessCapturedAsync, а не новую доставку. Recovery.rows означает право на будущую попытку. Точное восстановление всех повторных отправок из существующей БД невозможно. Для первого этапа дополнительно к attempts/recovery итоговый read-only агрегат по существующему журналу даёт `observed_repeat_captures = sum(max(capture_entries_per_delivery - 1, 0))` для кампании. Это нижняя граница повторных захватов с `journal_non_atomic=true`; не повторные отправки и не точный номер попытки. Не получать временной ряд повторов ежесекундным сканированием журнала. Для маленькой контролируемой acceptance-фикстуры истинная последовательность известна driver, что позволяет проверить отличие этих величин. Подробный аудит попыток — отдельное будущее решение.

### 3. Локальный экспорт агрегатов вместо обязательного сервера

Встроенный `MeterListener` получает измерения и накапливает thread-safe счётчики/гистограммы с атомарным закрытием окна. Точки окончания операции определяют её окно; длительность пересекающей границу операции целиком относится к окну окончания. В hot path нет файлового/сетевого I/O. Регистрацию listener завершить до старта worker, отключённый режим не создаёт файлов/таймеров сбора. Runtime metrics собирать тем же способом; CPU/RSS — периодическим Process snapshot. Это избегает обязательного диагностического сокета/privileged sidecar в Docker Desktop.

Интервал приложения по умолчанию 10 s, закрывается по монотонному времени. Для корреляции сохраняются UTC start/end, mono duration, offset от session epoch. Первое/последнее окна могут быть частичными. Коллекции с недопустимым временем или clock jump >1 s помечаются; анализ не склеивает их принудительно. На preflight оценить расхождение Windows/контейнеров/БД запросами с локальными границами RTT; сохранять интервал неопределённости (как минимум RTT/2), повторить в конце. В единой локальной VM это обычно мало, но не предполагается нулём.

Фиксированные непересекающиеся histogram buckets в миллисекундах: 0 отдельно, затем верхние границы `0.01 * 1.1^k` до >=600000 ms и overflow. Формат хранит точный массив границ, count по корзинам, count/sum/min/max. Размер ограничен количеством операций и категорий. p50/p95/p99 выдавать с нижней/верхней границей корзины и методом nearest-rank; без обещания точности лучше корзины (~10% по соседним границам), overflow не выдаёт конечный p95. Для n<20 p95 маркировать как малую выборку, для n=0 — null. Точность замера ограничена timer resolution, планировщиком, сбором и границей операции; десятичные разряды не равны точности.

Общий percentile: только сумма bucket counts одинаковой schema, операции, исхода и временного покрытия. Нельзя усреднять p95, percentile от средних или разные операции. Разные окна процессов нельзя точно разрезать по времени без сырых событий: график сохраняет per-process окна; сводная 60-s серия объединяет целые полностью покрытые окна с сопоставимыми границами (допуск 1 s, ошибка границы видима). Несогласованные/неполные окна оставлять отдельными; не делить histogram пропорционально и не называть получившееся точным общим p95. В одно-worker профиле этой проблемы нет.

Альтернативы: Prometheus/Grafana/OTel collector полезны для постоянной эксплуатации, но добавляют сервисы и хранение; сейчас не обязательны. `dotnet-counters` оставить опциональным диагностическим средством, не считать его экспорт p95 достаточным для объединения histogram. Полная запись каждой операции увеличивает I/O и объём — в первом этапе не применяется. Официальные основания: [сбор .NET metrics и MeterListener](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/metrics-collection), [dotnet-counters](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-counters).

### 4. Минимальные внешние снимки и стоимость

Отдельный Python driver управляет Compose, сбором и артефактами; использует docker CLI и psql внутри отдельного контейнера/БД. Python stdlib для файлов/оркестрации, зафиксированная plotting dependency только для отчёта. Образ приложения не зависит от Python. Сборщики не держат длительных транзакций, не сбрасывают статистику БД, не делают EXPLAIN ANALYZE на рабочем пути.

| Источник и default период | Минимальные показатели |
|---|---|
| Каждый .NET-процесс, 5 s | CPU cumulative seconds/cores, RSS/private bytes, managed heap bytes, allocation bytes delta, GC counts и pause seconds, ThreadPool queue/threads, exceptions; недоступные метрики явно missing |
| Контейнеры Worker/API/DB/HTTP-оператор и collector, 5 s | CPU utilization из Docker stats с нормализацией к cores, memory usage/limit и семантика cache, throttling при доступности, cumulative network rx/tx bytes, block read/write bytes, restart/OOM/health; производные bytes/s по фактическому времени |
| Windows/VM, 15 s | доступная/общая RAM, CPU load, disk bytes/s при доступности, ресурсы Docker VM; невозможность видеть соседнюю нагрузку — ограничение |
| PostgreSQL, 15 s | pg_stat_database commits/rollbacks, blocks hit/read, temp bytes/files, deadlocks; pg_stat_activity агрегаты state/wait_event_type/wait_event без query text; pg_stat_wal bytes/records, pg_stat_io и checkpointer при доступности |
| Таблицы/индексы, 60 s | relation/index bytes, estimated live/dead tuples, vacuum/analyze timestamps и counts для deliveries/journal/campaigns; estimates не выдавать за точные строки |
| Очередь, 30 s | точные Waiting у запущенной кампании, InProgress, expired leases, Sent/Failed, возраст старейшего Waiting по CreatedAt; отдельно eligible и total Waiting |
| Перед стартом/после остановки | точные счётчики кампании/журнала, observed_repeat_captures, версии PostgreSQL/.NET/Python/Docker, настройки статистики, размеры отношений |

Возраст по CreatedAt означает возраст с формирования, не время с последнего recovery. Отсутствующая очередь → oldest_age=null, а не 0. Все queue-агрегаты одного запроса имеют snapshot и start/end/DB-now. Query scope — единственная кампания сеанса, не все пользовательские данные.

Снимки pg_stat_activity — частоты наблюдения состояний, не точное распределение времени ожиданий и не список причин. Накопительные значения сохраняются с stats_reset/server-start; delta через reset — missing. I/O timing зависит от настроек, не включать автоматически track_io_timing/pg_stat_statements. Отдельный collection connection учитывается и исключается из числа рабочих соединений. Права/версия и недоступность сохраняются. Основание: [PostgreSQL 18 statistics](https://www.postgresql.org/docs/18/monitoring-stats.html).

Бюджеты defaults: запрос очереди statement_timeout=1 s, прочая SQL-статистика=500 ms, один активный запрос на collector, без catch-up после задержки. Частота может быть уменьшена до старта; если timeout — сохранить gap, не повторять немедленно. Длительность каждого sample, запаздывание, CPU/RSS collector, output bytes и dropped intervals входят в собственный ряд. Точная GROUP BY на 300k строк может быть дорогой: это предмет overhead-приёмки; сокращение частоты допускается только с записью изменения профиля, иначе сравнимый участок прерывается.

### 5. Файловый контракт, корреляция и аварийное окончание

Каталог `artifacts/performance/<session-uuid>/` вне Git. У каждого процесса собственный файл, общий append файл несколькими процессами запрещён. Доступ — текущему пользователю; автоматической отправки ИИ или стороннему серверу нет.

| Артефакт | Содержание |
|---|---|
| `manifest.json` | schema version, session UUID, commit/dirty flag и безопасный hash исходников, image digests, tool versions; allowlist effective settings и их hash; профиль нагрузки/размеры сообщений без текста; environment, campaign UUID, planned/observed participants, start/stop и причины |
| `metrics-schema.json` | определения, границы, единицы, категории, histogram bounds и алгоритмы анализа |
| `processes/<instance>/intervals-*.jsonl` | интервальные delta+cumulative счётчики, histogram, in-flight, completeness; ProcessInstanceId UUID, роль, WorkerId mapping, boot/start UTC |
| `samples/{containers,host,postgres,queue}.jsonl` | отдельные snapshots с collector instance и счётчиком последовательности |
| `lifecycle.jsonl` | preparing/ready/processing/draining/completed/aborted/stalled, присоединение/исчезновение процессов, marker отмены, collector failures; только безопасные коды |
| `summary.json`, `series.csv`, `report.html`, `charts/*.svg` | производные результаты, quality, статистика окон и графики; отчёт читает файлы без работающего приложения/БД |
| `checksums.json` | hash закрытых файлов и список ожидаемых источников; отсутствие hash у открытого хвоста допустимо |

Envelope JSONL: `schema_version, session_id, source, instance_id, sequence, start_utc, end_utc, duration_s, elapsed_start_s, elapsed_end_s, quality, metrics`. Значения метрик сопровождаются определением unit и kind (delta/cumulative/gauge/histogram); длительности ms, стеночное время s, работа deliveries и deliveries/s, память/I/O bytes, CPU seconds и cores; проценты содержат явный denominator (1 core/allocated capacity). Сетевой и блочный трафик не равен времени I/O. При несовпадении schema анализ завершается понятной ошибкой, а не молча преобразует данные.

Процессы связываются SessionId + instance UUID; PID и имя контейнера только метаданные, поскольку переиспользуются. Python-оператор не получает заголовки трассировки и не хранит данные: его контейнерные samples связаны manifest, длительность запроса измеряется на стороне клиента. Временной корреляции достаточно для первого этапа, доказательства точной внутренней серверной задержки нет.

Пример счётчиков закрытого окна (сокращённо, числа условны):

```json
{"schema_version":1,"session_id":"<uuid>","source":"worker","instance_id":"<uuid>","sequence":2,"start_utc":"2026-10-31T17:00:10Z","end_utc":"2026-10-31T17:00:20Z","duration_s":10.0,"elapsed_start_s":10.0,"elapsed_end_s":20.0,"quality":"complete","metrics":{"terminal.sent.delta":1200,"terminal.failed.delta":0,"terminal.sent.cumulative":2350,"processing.terminal_path_complete.delta":1199}}
```

Обновление manifest через temp+atomic replace; lifecycle сохраняется сразу. Закрытые JSONL-записи flush каждые 10 s; максимум три закрытых окна в bounded export queue, отдельный writer, память диагностики <=16 MiB на процесс. Rotation по 64 MiB; общий лимит сеанса 2 GiB по умолчанию. При заполнении/ошибке записи не удалять ранние файлы: прекращать сбор с безопасной ошибкой, driver помечает telemetry_failed. Пропуски очереди экспорта учитываются; collector heartbeat/отсутствие финального маркера позволяют выявить потерю процесса, даже когда он не мог записать ошибку.

Чтение оборванного JSONL принимает только полные валидные строки до повреждённого хвоста; не игнорирует ошибку в середине файла. Дубликаты по instance+sequence отбрасываются только при идентичном содержимом, конфликт — ошибка качества. SIGKILL процесса теряет открытое окно, до трёх ожидающих окон и выполняемую writer запись, но не закрытый сброшенный префикс. При исправном writer типичная потеря ограничена текущим 10-s окном; при задержках/переполнении нельзя обещать фиксированную границу потери в секундах: отчёт использует последнюю читаемую точку и dropped markers. При штатной остановке закрыть partial window и дождаться writer в пределах 5 s внутри существующего shutdown budget, без изменения HostOptions ради диагностики. Падение Windows/Docker VM/питания может потерять и OS-cached данные: flush не обещает fsync durability. Отдельный режим fsync, если потребуется, сначала проходит оценку накладных расходов.

DB commit и запись счётчика не атомарны. Commit с потерянным ответом, авария до Counter.Add или незаписанный хвост дают расхождение с финальным SQL-снимком. Итог включает `db_terminal_delta`, `observed_terminal_applied`, разницу и причину/unknown; не распределяет остаток задним числом по окнам. После обычной успешной остановки в изолированном прогоне требуется точное совпадение, после аварии данные только в пределах покрытия. Журнал не является безусловной истиной для этих счётчиков.

Пропуск ≠ ноль. Полный интервал живого источника с нулём событий показывает 0; исчезнувший источник — null. Late samples остаются со своим event time, receipt time и lag, без интерполяции. Сумма процессов при неполном наборе помечается partial/lower-bound, её не сравнивают с полной baseline. Перезапуск не обнуляет SessionId, но создаёт новый instance и разрыв baseline.

Privacy: allowlist параметров вместо дампа environment/compose config/docker inspect/SQL logs. Исключить connection string/password/token, email, тела запросов/ответов, message text, recipient IDs, полные URL и exception messages/stack traces. Допустимы synthetic campaign UUID и технические instance IDs; имена кампаний не нужны. Файлы не включают полные stdout/stderr неизвестных команд. Секретные значения не хешировать в публичный manifest. Автоматическая очистка — только явная команда по SessionId, после отчёта ничего не удаляется.

### 6. Порядок запуска и завершения

Будущие интерфейсы driver (имена — целевой контракт реализации, сейчас таких команд ещё нет):

```powershell
python scripts/performance/run.py --profile windows-http-300k --output artifacts/performance
python scripts/performance/analyze.py --session artifacts/performance/<session-id>
python scripts/performance/stop.py --session artifacts/performance/<session-id>
```

1. Preflight читает версии, фактические ресурсы и allowlist-конфигурацию, проверяет Windows Docker Desktop/Linux containers, свободное место для БД и лимита файлов, права записи volume. Создаёт новый project `packcall-perf-<uuid>`, собственную БД/volume, порты только localhost и SessionId. Никаких TRUNCATE или down -v на dev project.
2. Собрать Release images и зафиксировать digests; поднять БД, migrator, API и оператор с healthchecks. Seed параметризованно создаёт ровно 300 000 синтетических получателей в новой БД; API формирует единственную Draft кампанию, SQL сверяет 300 000 Waiting, 0 InProgress/Sent/Failed. Сохраняются подготовительные start/end, размеры/статистика БД и результат ANALYZE, если оно входит в фиксированный setup; этот выбор одинаков в сравниваемых прогонах.
3. Поднять worker с включённым сбором; пока кампания Draft, отправки нет. Дождаться ready всех collectors и первого контрольного файла каждого процесса, проверить отсутствие чужих workers/кампаний. Установить processing epoch непосредственно перед API start; сохранить driver request/response границы и бизнес StartedAt отдельно. Мониторинг начинается раньше epoch, поэтому первая обработка не пропускается; пограничное окно помечено.
4. Ничего не менять и не добавлять в течение прогона. Сбор очереди/ресурсов идёт с фиксированными периодами; паузы хоста, рестарты, новый процесс или ручное вмешательство отмечают нарушение профиля. Watchdog отсутствия прогресса 120 s только создаёт stalled marker; не перезапускает и не лечит приложение.
5. Нормальное завершение: SQL показывает 300 000 терминальных строк, campaign Completed; driver ждёт quiescence in-flight и штатно останавливает worker, затем получает финальный снимок БД и сброс файлов. `last_terminal_confirmed`, `campaign_completed_observed`, `processing_stopped`, `collection_stopped` — отдельные моменты. Последний terminal может предшествовать окончанию последнего journal/check; наблюдение Completed опросом задаёт интервал неопределённости, не точный момент commit.
6. Финализировать manifest/checksums, построить отчёт офлайн. Независимые поля `workload_status` и `telemetry_status`: успешный workload с неполной телеметрией не означает успешную приёмку измерения. Ctrl+C сохраняет abort reason и штатно завершает именно project сеанса, оставляет БД/файлы для разбора; принудительная остановка поддерживается анализатором как partial. Повторный запуск создаёт новый сеанс и новую БД; явная cleanup-команда ограничена зарегистрированными ресурсами этого сеанса.

### 7. Анализ во времени без предположения о деградации

Графики: throughput Sent/Failed/total и finished attempts; p50/p95/p99 для операций с count и погрешностью; очередь/возраст/пустые захваты/in-flight; CPU/RAM/GC/I/O/ожидания; elapsed time и накопленный terminal volume, размеры таблиц. Отдельные панели вместо двойных осей с произвольным масштабом. HTML офлайн без CDN; SVG и CSV позволяют повторный анализ, AI получает summary+manifest+schema+JSONL без извлечения графика.

Defaults анализа (изменяемые параметры, сохраняемые вместе с версией анализатора):

- Первые 60 s после processing epoch — candidate warmup, не удалять из файлов. Показать чувствительность выводов при 30/60/120 s. Это не гарантия завершения прогрева: если показатели продолжают меняться, baseline не объявлять устойчивой.
- Чистое окно: все ожидаемые источники доступны, нет рестарта/clock jump/config/load change, не partial. «Достаточная очередь» по соседним queue samples: eligible Waiting > max(10×W×P×B, 60×r), где r — terminal/s предыдущего полного 60-s окна, без пустых/неполных захватов. При неизвестном r первоначально использовать 10×W×P×B. Наблюдение раз в 30 s не доказывает непрерывный запас: это консервативный eligibility-фильтр с явной неопределённостью; пограничные участки исключать из сильных выводов.
- Сводные окна 60 s. Устойчивый кандидат — минимум три последовательных чистых окна после warmup, каждое в пределах ±10% медианы их throughput; указать min/max, variance и наклон. Baseline — первая последовательность из пяти чистых окон, каждое в пределах ±10% медианы throughput этой пятёрки; если её нет, устойчивость baseline не установлена. Не выбирать наиболее быстрые окна задним числом.
- Возможное замедление — не менее трёх последовательных чистых 60-s окон ниже baseline median более чем на 10%, при достаточной очереди. Указать первое окно, время/объём до него, длительность и возможный интервал начала, а не точную секунду. Это эвристика обнаружения, не статистическое доказательство; дать результат и для порогов 5/10/20%.
- Если operator.call p50/p95 растёт (с учётом границ корзин), пометить сопутствующее изменение клиентского пути оператора. Изменения сети, планировщика и сервера неразличимы этим таймером. Очередь/пустые захваты определяют хвост, не деградацию. Рост таблиц и elapsed time в одном прогоне взаимосвязаны: их причины разделяет будущий контролируемый эксперимент, не корреляция.

При 300k сеанс может закончиться раньше нужного числа окон: вывод `insufficient_data`, длительность подтверждённой устойчивости ограничена фактически наблюдавшимся периодом. `no_slowdown_detected` означает только отсутствие обнаруженного замедления в пригодных окнах с указанными порогами. Отчёт содержит наблюдения, гипотезу, альтернативы и проверочный эксперимент с изменением одного фактора; никакого автоматического «PostgreSQL виноват».

### 8. Проверка корректности и бюджета наблюдения

Контрактные проверки на fake time/управляемых зависимостях: N успешных сохранений, M Failed, false result, operator timeout, отмена до/после сохранения, ошибка журнала после true, pause return, lease skip, recovery SQL succeeded/journal failed. Проверять конкретные счётчики и count гистограмм, отсутствие отрицательного времени, инварианты cumulative и смены окон под concurrency. Контролируемая задержка 100 ms должна дать длительность в [100 ms, 100 ms + допустимый scheduler tolerance], а fake monotonic time — точное ожидание; wall-clock jump не меняет длительность.

Изолированный PostgreSQL + реальный HTTP smoke: малое известное число доставок, без сбоев и с управляемым сбоем после commit; агрегаты сверяются с финальными строками, без payload export. Два процесса с заведомо разными распределениями проверяют merge, reset, missing source и последнюю partial window. SIGKILL, оборванная строка, disk error/лимит, остановка driver проверяют префикс и статус partial; исправные закрытые строки не теряются и не переписываются.

Накладные расходы проверяются отдельно от одного пользовательского сеанса: минимум три пары fresh 300k прогонов off/on в чередующемся порядке, те же image digest, seed, P/B, ресурсы и HTTP-режим; off отключает инструменты/внешние polls, оставляя одинаковые начальный/финальный снимки. Измерять throughput на одинаковом пригодном объёме/фазах и общую длительность, CPU seconds и peak RSS контейнеров, DB I/O/WAL и output bytes. Собственная цена driver/collector видна отдельно. Получение ресурсных endpoints off не превращать в полный мониторинг; минимальный reference sampler одинаков в обоих режимах и его стоимость записана.

Предложенный бюджет: median потери throughput <=5%, изменение p95 processing <=10% при сопоставимых окнах и достаточных samples; диагностика Worker <=16 MiB памяти, collector peak <=128 MiB и mean <=0.1 CPU core, файлы <=2 GiB/сеанс. Показать все пары и разброс. Если естественный разброс throughput между off-прогонами >5%, сравнение неубедительно: overhead status=inconclusive, улучшить изоляцию и повторить, не принимать формальный pass. Если бюджет превышен — отчёт failure с конкретными затратами; изменение периодов/формата требует нового зафиксированного профиля и повторной проверки, без оптимизации бизнес-кода.

## Risks / Trade-offs

- [Длительность прогона 300k заранее неизвестна] → не обещать часы устойчивости; короткий прогон даёт недостаток данных, увеличение объёма отдельным сеансом согласуется позже.
- [Docker Desktop VM, фоновые приложения, sleep Windows] → сохранять доступные ресурсы, запретить sleep на время сеанса в runbook, отмечать вмешательство; CPU контейнера не равен CPU Windows.
- [Само чтение queue и pg stats влияет на БД] → budgets/timeout, стоимость samples и off/on-приёмка.
- [Пропуски между commit, журналом и метриками] → сверка итогов и явная неполнота, без транзакционного изменения приложения.
- [Файловые операции на Windows bind volume медленны] → отдельный writer и bounded buffer; сравнить стоимость на фактическом mount, не скрывать её RAM-буфером без границы.
- [Корреляция выглядит убедительно] → разделять наблюдение и гипотезу, требовать контролируемую проверку.

## Migration Plan

Новая диагностика выключена по умолчанию. Развёртывание только через явный performance profile и overlay; общие настройки запуска сохраняют прежние значения. Миграция БД не нужна. Сначала контракты и малый smoke, затем off/on оценка, после неё пользовательский 300k сеанс. Откат — выключить профиль, остановить collector; старые файлы читаются по версии или получают явную ошибку несовместимости. Результаты и isolated volume не удалять автоматически.

## Open Questions

Конкретные CPU/RAM Windows и Docker VM, backend и доступность I/O/throttling узнаются preflight перед первым запуском. Они не меняют файловый контракт и план; manifest обязан описать фактические значения и пробелы. Порогов детектора недостаточно для SLA: их пригодность будет оцениваться на собранных рядах без ретроспективной подгонки исходных данных.
