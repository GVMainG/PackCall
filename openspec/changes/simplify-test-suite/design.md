## Goals / Non-Goals

**Goals:** независимые понятные наборы; единственный владелец общей подготовки; наблюдаемая полнота прогонов; сохранение причинно различающихся сценариев. Каждому сокращению соответствует строка D1–D6 и отчёт сопоставления assertions.

**Non-Goals:** менять бизнес-алгоритмы, публичные API, числовые статусы, production Compose-поведение, версии пакетов, схему БД или формат измерений; добавлять автоматическую отмену кампании, восстановление formation после аварии, тесты результатов новых замеров. Отмена здесь — токены формирования/отправки, lease budget и shutdown. Не объединять поведенчески разные SQL-гонки ради короткого файла.

### 2. PostgreSQL: общая БД, отдельное состояние

Python launcher создаёт один PostgreSQL-контейнер на полный C# integration-прогон либо использует явно переданный принадлежащий этому прогону acceptance PostgreSQL. Не запускать весь integration повторно в каждом режиме B11: выделить один обязательный общий gate; транспортные сценарии остаются в собственной матрице. При прямом `dotnet test` отсутствие `PACKCALL_TEST_POSTGRES` должно давать ошибку, а не PostgresFact Skip.

`tests/PackCall.IntegrationTests/Support/PostgresFixture.cs` хранит проверенные настройки подключения; `PostgresTestScope.cs` создаёт уникальную schema, provider и contexts на тест и освобождает их до DROP. Стандартный путь применяет настоящие EF migrations. SearchPath и migration history изолированы в тестовой schema; не допускать fallback к public. До перехода проверить две независимые схемы, их histories и повторный MigrateAsync. Если понадобится настройка history, она остаётся в тестовой фабрике, без правки production migrations.

`SchemaGateTests` явно запрашивает schema без автоматической миграции: сохранить последовательность ожидание → точная история → неизвестная миграция → cancellation, без конфликта CREATE HISTORY с мигрированным setup. Это тест startup gate, а не доказательство физической целостности БД. Реальный Migrator, повторное применение и API/Worker startup остаются в Docker.

У каждой стороны SQL-гонки собственный DbContext/connection и собственная транзакция, как сейчас. Общие helpers `DatabaseNow`, `WaitBlocked`, snapshots/journal принадлежат `Support/PostgresAssertions.cs`, а orchestration гонки остаётся видимой в тесте. Не оборачивать тесты в общий rollback. Все waits, commands и disposal имеют бюджет. Не использовать production-подключение; launcher передаёт только endpoint своего PostgreSQL, уникальные имена и владение фиксируются в метаданных.

Альтернатива Testcontainers отложена: она не убирает Compose, процессы, сигналы и барьеры. Общий mutable context и базовый partial-класс отвергнуты: они скрывают сессии и связывают независимые модули.

### 3. Небольшие общие Python-функции

Добавить `tests/support/{processes.py,docker.py,dotnet.py}` и явный launcher `tests/run_tests.py`; стандартная библиотека, без DSL, регистрации сценариев и иерархии runner-классов. `processes.py`: subprocess с timeout, stdout/stderr, monotonic wait, HTTP с timeout. `docker.py`: Compose/SQL, readiness, проверка владения, snapshot/log collection, cleanup. `dotnet.py`: publish/build и проверка TRX. Импортировать через явный путь от repo root, чтобы запуск из любого cwd не ломался.

Передавать run directory/project/container IDs/connection явно. Метаданные `run-context.json` содержат run ID, status, абсолютный output directory, repo root, Compose project и идентификаторы созданных ресурсов с labels. Проверять Docker labels/IDs до stop/restart/rm/TRUNCATE. Не доверять одному имени, `latest-run.txt` или найденной строке commands.jsonl. Устаревший pointer может выбирать сеанс только после валидации метаданных; для destructive operations требовать явно выбранный контекст. Контейнеры и output уникальны на запуск, host ports только loopback, cleanup в finally лишь своего набора. Для подключённого сеанса восстанавливать исходное running-состояние БД.

Публиковать API/Worker/Migrator и probes один раз в пределах текущего прогона и конфигурации; не вводить глобальный кэш. B11 `run.py`, W21 `startup.py`, `configuration.py`, `lifecycle.py`, `images.py`, `compose-failure.py`, W22 `run.py`/`verify.py` используют функции без изменения своих assertions. B11 остальные сценарии (`operator_contract`, `config_matrix`, `precedence`, `privacy`, `prod_compose`, `late_http`) также подключать по необходимости повторяемой обвязки. `scripts/performance/postgres_tests.py` делегирует C# gate, `crash_smoke.py` переиспользует publish helper. Рабочие `scripts/performance/{run,collectors,reader,analyze,session,stop,cleanup}.py`, SQL и schemas не реорганизовывать ради унификации тестовых команд.

TRX: требовать существующий корректный отчёт, total>0, total=passed, ноль failed/skipped/notExecuted; сверять ожидаемые обязательные группы/параметры с этапным реестром. Process exit=0 без отчёта недостаточен. Для acceptance сверять все обязательные scenario keys, включая W22-01..05; результат passed писать только после всех gates. Сохранять результаты текущей попытки и при ошибке, с командой/таймаутом/stdout/stderr и доступными SQL/Compose/log snapshots до уборки. Не ослаблять существующий `test_harness_fixes.py` при адаптации к общим функциям.

### 5. Уточнение критичных проверок

- `tests/PackCall.UnitTests/Deliveries/DeliveryTests.cs`: таблица `DeliveryStatusTransitions` по всем известным состояниям; оба terminal-метода из InProgress ставят даты и очищают lease, из Waiting/Sent/Failed выбрасывают доменную ошибку без изменения полей. Для setup разрешён существующий test-only helper. Waiting→InProgress и recovery — реальные SQL-тесты, не придуманные методы Delivery. `CampaignTests` сохранить даты/идемпотентность, явно покрыть команды из Forming/Failed/Paused вместе с Draft/InProgress/Completed по текущим правилам.
- `tests/PackCall.IntegrationTests/Campaigns/CampaignFormationPostgresTests.cs`: вызвать настоящий CampaignService поверх реальных repositories с узким декоратором для сбоя второй порции и отмены после первой уже закоммиченной порции. ### 6. Синхронизация и комментарии

Исправление трёх сообщений `DeliveryWorker.cs` и `late_http.py` делать одним этапом. Не привязывать тест к переводу текста. Сохранить наблюдение именно истечения lease budget старого worker, а не одного лишь Sent нового: добавить стабильный код `LeaseBudgetExpired` через placeholder `{EventCode}` в соответствующий существующий Warning (без нового public API/метрики) и ждать его с worker/delivery identity и timeout; при timeout сохранять logs+SQL snapshots. Текущий console outputTemplate выводит Message, но не произвольные Properties, поэтому код должен быть виден в rendered message без изменения конфигурации логирования. Это узкое изменение логирования, не production test switch. Сохранить задержанный настоящий HTTP-ответ и сравнение состояния после ответа.

Содержательные комментарии на русском, идентификаторы/протоколы/ключи/коды неизменны. Объяснять: в `DeliveryRepository.cs` время после lock и owner+expiry, повторную проверку recovery и EF detach; в `DeliveryWorker.cs` бюджет общего пакета и монотонное время; в `DeliveryProcessingService.cs` неопределённый исход и отдельный бизнес-журнал; в `CampaignService.cs` компенсацию без общей транзакции и None для cleanup, отсутствие crash recovery/единого снимка аудитории; в `SchemaGate.cs` доверие истории; в Diagnostics/MeasurementHost ограниченные категории, отсутствие I/O на delivery path и потерю телеметрии. В Python/SQL гонках объяснять независимые сессии, условия барьеров и атомарную публикацию; в performance анализе — пропуск≠ноль, объединение распределений, нижнюю границу повторов и пределы корреляции. Не добавлять пояснения очевидным вызовам. Designer/snapshot и прочие generated-файлы не редактировать ради перевода.

## Risks / Trade-offs

- Потеря theory строк при split → до/после каждого этапа сохранять discovery/TRX и соответствие старых и новых имён с параметрами; не ориентироваться только на общее число.
- MigrateAsync видит public history или SchemaGate setup конфликтует с общей фикстурой → независимые histories и специальный raw scope, отдельная проверка двух схем и повторной миграции до удаления CreateTablesAsync.
- Новый порядок tests меняет глобальные listeners → сохранить Measurement collection и последовательный gate, освобождать listeners/providers до следующего теста.
- Уборка/SQL задевает чужие Docker-ресурсы → run-context + labels + реальные IDs, отказ при несовпадении до мутации; никаких global prune/фиксированных production-имён.
- Слишком большой helper → только функции трёх модулей; сценарии и assertions остаются видимыми в runner, без DSL и новых зависимостей.
- Усиленный тест выявляет реальный бизнес-дефект → не менять ожидаемое поведение и не исправлять алгоритм молча; сохранить воспроизведение, зафиксировать отдельную проблему и согласовать изменение scope.
- Полная приёмка дорога → последовательные gates по этапам; последний полный прогон один раз после завершения изменений. Зелёный unit не заменяет integration/W22.

## Migration Plan

1. **Структура:** зафиксировать baseline сценариев/строк, разнести проекты/классы и обновить пути, ничего не удаляя. Gate: оба проекта собираются, объединённый список сценариев и строк соответствует исходному, полный C# прогон на Docker PostgreSQL без skips.
2. **Фикстуры и обвязка:** общий PostgreSQL, миграции, raw SchemaGate scope, общие helpers/publish/TRX/resource context. Gate: повторный integration-прогон на свежем окружении, SQL-race tests без общего rollback, негативные проверки отсутствия БД/TRX, timeout/чужого контекста; существующие harness tests проходят.
3. **Доказанные сокращения:** по одной D1–D6 с предварительным сохранением отличающихся assertions. Gate: таблица старое→оставшееся с результатами и риском, соответствующие C#/Docker сценарии проходят; W22-01..05 сохранены.
4. **Уточнения:** домен, компенсация, SendResult, callback/file failure. Gate: проверяется настоящее поведение, а не логика фейка; все действующие проверки измерений сохранены. Никаких новых тестов результатов измерений.
5. **Комментарии и logs:** согласованно исправить Warning/late_http, перевести содержательные пояснения. Gate: реальный late HTTP и shutdown проходят, нет испорченных строк в затронутых исходниках, generated diff отсутствует.
6. **Итог:** unit без инфраструктуры; integration на Docker с zero skips; W21/B11 и W22 в существующих реальных режимах; Python performance unit-набор и существующие control/crash/stall/resource/two-worker smoke. Сохранить команды, вывод, TRX, scenario results и список ожидаемых проверок. Не запускать новый нагрузочный профиль ради этого change.

Rollback — отдельный обратимый diff каждого этапа: вернуть пути/entrypoints/фикстуру соответствующего этапа; production-data migration не требуется. Не восстанавливать удалённые тесты из памяти: они остаются в истории Git до подтверждения D1–D6. Planning в этой сессии завершить без исполнения этих шагов.
