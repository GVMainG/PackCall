# GitHub-задачи PackCall

Создавай задачи как краткий контракт результата, а не как подробное ТЗ или готовое решение.

## Контекст и инструменты

1. Сначала прочитай skill `github:github`.
2. Убедись, что локальный remote указывает на `GVMainG/PackCall`. Не применяй этот skill к другому репозиторию.
3. Для чтения и изменения Issues используй GitHub connector: `fetch_issue`, `create_issue`, `update_issue`. Не создавай Issue без явной просьбы пользователя.
4. Перед редактированием получи текущую версию Issue. Сохраняй пользовательские правки, если пользователь не просит заменить их.

## Формат задачи

### Заголовок

Используй форму: `<этап> — <раздел> — <действие>`.

Пример: `MVP — бизнес-модель данных — спроектировать бизнес-сущности`.

Название должно быть кратким, понятным вне контекста и описывать результат, а не технический способ его достижения.

### Описание

Используй только необходимые разделы:

```md
# Зачем

Краткая ценность результата: 1–2 предложения.

# Что сделать

1. Результат или подзадача.

# Входные артефакты

- `путь/к/документу.md`

# Результат и критерии готовности

- [ ] Проверяемый результат.

# Вне рамок задачи

- Ясная граница текущей работы.
```

Не добавляй раздел, если он не даёт необходимого контекста. Критерии должны описывать наблюдаемый результат, а не способ реализации.

## Границы детализации

- Не предрешай за пользователя сущности, поля, архитектуру, технологии, крайние случаи или декомпозицию, если они ещё не согласованы.
- Не превращай Issue в ТЗ. Решения вырабатываются отдельно и фиксируются в документации проекта.
- Не добавляй собственные TODO, чек-листы, оценки, метки или исполнителей без явной просьбы.
- Указывай технические решения и детали реализации только когда пользователь уже принял их или прямо просит включить.
- Чётко отделяй результат текущей задачи от следующего уровня работы. Например, бизнес-модель данных не включает выбор СУБД, индексы и миграции.

## Проверка перед созданием или обновлением

- Заголовок соответствует формуле «этап — раздел — действие».
- Текст отвечает на «зачем» и «что должно получиться».
- Входные документы перечислены, если без них нельзя понять задачу.
- Критерии готовности можно проверить по итоговому артефакту.
- В задаче нет несогласованных решений и лишней технической конкретики.
